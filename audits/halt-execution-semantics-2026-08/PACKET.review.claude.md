## Design, restated (proof of reading)

The packet decouples two truths the DAILY path (`cli_main`/`execute_run`) currently conflates in one field:

- DOMAIN status stays FAIL for any system halt (built at `_build_run_summary` runtime/__init__.py:1436; enforced by verify :1757 and check_readiness :96). No flip. `system_halted`/`outcome=HALT`/`errors`/`kill_switch` preserved verbatim.
- A NEW in-memory EXECUTION-SUCCESS signal drives the exit code instead of `status==SUCCESS`. Predicate (s3 D-CORE:44): `execution_success = verification.pass AND (status==SUCCESS OR (system_halted AND halt_cause==MARKET_STRESS))`. Computed in `execute_run`'s success branch where `pipeline.validation_summary.halt_cause` is in scope (confirmed reachable: PipelineResult carries `validation_summary: ValidationSummary`, _types.py:64; the replaced carrier at runtime :1031-1036 sets `halt_cause=MARKET_STRESS`). `cli_main` (:237) returns `0 if execution_success else 1`. No persisted field is added.

Consequence: a valid market-stress kill-switch halt exits 0 -> the existing workflow sets `PUBLISH_READY=true` (cuttingboard.yml:298, keyed on rc==0) -> renders + `check_readiness --profile morning` passes it (:96-97) -> commits/pushes the halt board (:387/:438) -> `conclusion=success` -> satisfies the OPEN slot for the Cloudflare first-success coordination. A VALIDATION/data-integrity halt (errors non-empty) and any crash stay exit 1, no publish. The DAILY path additionally always-sends its single halt notification for a market-stress halt (bypassing the `should_send` state-key dedup at :910) to close a ZERO-notification hazard, without touching the hourly path or `classify_notification_priority`. The design cites the HOURLY path (`_execute_notify_run` persists status=FAIL :583, returns SUCCESS :645; alert_runner exits `0 if SUCCESS` :116) as the proven precedent.

## VERDICT

REQUIRED CHANGES (2). The core split is sound, the masquerade analysis is correct on the reachable paths, domain truth is preserved, and the notification hazard analysis holds. Two corrections are needed before the design is frozen for Stage-0, both cheap and within GOV-2's single bounded correction cycle: (1) the frozen D-CORE predicate must encode the `errors==[]` guard its own s2 discriminator and "NO MASQUERADE PATH" claim rely on; (2) the packet must specify the execution-success return carrier (post-persistence, both `execute_run` return paths, `cli_main` absent-key handling) so Stage-0 cannot implement it as a boundary-violating persisted field or a fail-open on the exception path.

## REQUIRED CHANGES

1. **D-CORE predicate (s3:44) omits `errors==[]`, contradicting s2's stated discriminator and the "NO MASQUERADE PATH" claim (s2:35-39).** s2 states the discriminator is "`errors==[] AND halt_cause==MARKET_STRESS`" and asserts no masquerade path exists. But the FROZEN predicate at :44 is `verification.pass AND (status==SUCCESS OR (system_halted AND halt_cause==MARKET_STRESS))` - it does NOT test `errors`. I verified `verify_run_summary` (runtime/__init__.py:1668-1800) computes its `pass` as `not errors` over its OWN invariant list and NEVER inspects `summary["errors"]` emptiness (grep confirmed: the only match is `"pass": not errors` at the internal accumulator). So the predicate as written would promote a hypothetical `system_halted=True + halt_cause==MARKET_STRESS + errors!=[]` summary to exit 0 / publish. The design is safe TODAY only because of an un-encoded runtime invariant: the market-stress branch is the `elif` at :1022 and never appends to `errors`, while the sole pre-halt `errors.append` is the mutually-exclusive validation branch at :1020 (`errors` initialized empty at :955). The safety of the system's single highest-consequence exit/publish decision therefore rests on a code-structure invariant the frozen predicate does not state. Fix: encode the guard directly - `execution_success = verification.pass AND (status==SUCCESS OR (system_halted AND halt_cause==MARKET_STRESS AND not errors))` (or equivalently gate the whole halt clause on `not errors`) so the predicate matches s2, satisfies PRD-198 invariant #1 (fail-loud, never silent-fallback) and #3 (authoritative source - the same `errors` list check_readiness :94 uses), and cannot fail-open if a future refactor of the :1019/:1022 halt branches ever adds an error on the market-stress path. Ship the red test s6 already promises for this class, but make one case a constructed `MARKET_STRESS + errors!=[]` summary that MUST exit 1.

2. **The execution-success return carrier is under-specified, leaving two ways Stage-0 can violate the frozen boundary or fail-open.** D-CORE says the signal is "conveyed to cli_main WITHOUT persisting a new artifact field (contained return-contract change on the daily path; the summary dict is unchanged)." Two concrete hazards the packet must foreclose:
   (a) `execute_run` returns the SAME mutable `pipeline.summary` object it persists at :302-303. If Stage-0 sets `pipeline.summary["execution_success"]=...` before those rewrites, the field IS persisted - a `latest_run.json` schema change that trips the s4 FROZEN boundary ("No new persisted field") and the s9 STOP condition. The packet must state the carrier is added strictly AFTER persistence (after :303) or is a separate return value / typed carrier, not a key on the persisted dict.
   (b) The exception path (:315-349) returns a distinct `_failure_summary` dict that carries NO `execution_success` key (and `kill_switch=False`, no `halt_cause` key - :2554-2565). The packet's s5 cites only "execute_run:297-301" and never addresses this path. Stage-0 must guarantee both return paths convey the same contract shape and that `cli_main` treats an absent/False signal as exit 1 (a crash whose failure dict lacks the key must not fall through to exit 0). This is currently safe by construction (absent key -> falsy) but is unstated in a FROZEN design that Stage-0 will implement literally; name it. Recommend an explicit typed return (e.g. `(summary, execution_success)` or a small result object) over mutating the shared summary dict, which removes hazard (a) entirely.

## RECOMMENDED (non-blocking)

- **Path citation errors that will mislead the PRD-158 grep sweep / FILES.** s5 and s8 cite `cuttingboard/postmarket.py`; the file is `cuttingboard/reports/postmarket.py` (there is no `cuttingboard/postmarket.py`). s5 also cites "execute_run:297-301" for where execution-success is computed, but :297-301 is the existing status-override block; the new determination must run after `verify_run_summary` (:288) and read `pipeline.validation_summary`. Correct both so the Stage-0 FILES boundary and grep sweep target real lines.
- **Widen the postmarket-EVR Stage-0 test beyond the both-NEUTRAL case.** D-CONSUMERS reasons about the halt-as-prior only as "STAY_FLAT / no trade expectation" (benign). But `_classify_evr_with_levels` (reports/postmarket.py:64-101) will classify a SUBSEQUENT directional run against a NEUTRAL halt prior as an explicit "MISS" (:90-94: `prior_direction != realized_direction`), not merely the benign both-NEUTRAL branch (:83-88). This is acceptable because EVR is a display-only postmarket sidecar (it feeds no exit/publish/trade decision; VISION read-only-sidecar), but the packet's benign claim currently only covers the both-NEUTRAL path. The Stage-0 behavioral test (or the exclude-MARKET_STRESS-prior fallback) must explicitly cover the halt-prior -> directional-run MISS path, and the packet should state that "benign" is grounded in EVR being non-decision output.
- **Note the precedent is a strengthening, not exact parity.** The hourly `_execute_notify_run` returns SUCCESS on ANY non-exception completion (:645) and relies entirely on `check_readiness` to reject a VALIDATION halt at the artifact gate; it does NOT distinguish VALIDATION vs MARKET_STRESS at the exit code. The daily design is STRICTER (VALIDATION halt exits 1 by predicate AND fails readiness). That is better, not a defect - but the packet frames it as "parity"; call it a strengthened variant so the reviewer of PRD-298 does not expect the daily exit logic to mirror the hourly's unconditional SUCCESS return.

## ADVERSARIAL FINDINGS (what I tried to break, and what held)

- **A. MASQUERADE (crash/corruption exits 0):** HELD, modulo REQUIRED #1. A crash is caught at :315 and REPLACED by `_failure_summary` with `errors` non-empty, `kill_switch=False`, and NO `halt_cause` key (:2544-2565) -> predicate false -> exit 1. `execution_success` is computed from the in-memory `pipeline.validation_summary`, which is unbound in the exception path, so the computation is structurally confined to the success branch. `MARKET_STRESS` is set only at :1035, reachable only when validation did NOT halt (:1016 `if not system_halted` computes regime) and the kill switch trips on validated data (:1022) - so a kill-switch trip on unvalidated data is impossible (mutual exclusion :1019/:1022). The one gap is REQUIRED #1: the errors guard lives in the mutual-exclusion structure, not in the frozen predicate.
- **B. DOMAIN TRUTH (does it flip status?):** HELD. `execute_run` :297-301 promotes status to SUCCESS only when it is ALREADY SUCCESS and verify passes; a halt's status (built FAIL at :1436) is never touched. `execution_success` is a separate in-memory value. verify :1757 and check_readiness :96 never see a flipped status. No persisted schema change required (subject to REQUIRED #2 being implemented post-persistence).
- **C. NOTIFICATION EXACTLY-ONE:** HELD, hazard analysis is correct. I confirmed the LOW-priority premise: `derive_run_status` returns STAY_FLAT for a halt (contract.py:200-201), not "ERROR", so `classify_notification_priority` falls through to LOW (state.py:90) - a halt is genuinely dedup-suppressible. The ZERO hazard is real: `logs/last_notification_state.json` IS in the CI restore/publish set (cuttingboard.yml:157, force-added :401, pushed :438), so once a halt publishes it persists its dedup key, and the next identical halt would suppress (`should_send` :103/:110) with no `if:failure()` backstop (exit 0). The always-send fix is correctly scoped to the daily send gate (:905-910), touches neither the hourly path nor `classify_notification_priority`, and cannot double: under exit 0 the PRD-295 `if:failure()` step is dormant, and the runtime sends exactly once at :912. (Pre-existing, non-regressing: a crash AFTER the halt send at :912 - post-send work at :1242+ throwing - yields the halt send PLUS a failure-step send; this is today's behavior and is a correct degrade, not introduced here.)
- **D. CONSUMERS (first-ever halt publish):** HELD with the EVR caveat above. `_failure_summary`/halt writes zero evaluation records (a halt has no trade_decisions; `run_post_trade_evaluation` scores prior trades, not the halt); performance_engine drops non-terminal outcomes; regime_history folds a well-formed halt row without accuracy scoring; the commit-path `check_readiness --profile morning` (:417, under `set -e`) aborts publish on a malformed render BEFORE commit/push - so a broken halt board cannot reach the publish branch. The only new behavioral consequence is the EVR halt-prior (RECOMMENDED #2), which is display-only.
- **E. VERIFY/READINESS:** HELD. A market-stress halt board (status=FAIL, errors=[], system_halted=True, outcome=HALT, kill_switch=True, candidates_qualified=0 because the qualification block at :1038 else is skipped, regime computed at :1017 and valid, fresh timestamp) satisfies every verify invariant (:1749 no qualified trades, :1757 FAIL, :1759 HALT, :1765 system_halted) and passes check_readiness :96-97. A VALIDATION halt (errors non-empty) fails BOTH the predicate (exit 1) and readiness :94-95 - double-safe. A crash fails both. No halt sub-case passes the gates that shouldn't; no publishable sub-case fails them.
- **F. BOUNDARY:** HELD. No `latest_run.json`/contract schema change (subject to REQUIRED #2), no hourly change, no Cloudflare/authority surface, no workflow change (the rc==0 -> PUBLISH_READY -> commit/push chain at :298/:387/:438 already suffices). No RED/STOP condition in s9 is currently tripped.
- **G. COMPLETENESS:** Minor gaps only. FIXTURE-mode market-stress halt would also exit 0 by the predicate but never sends (`not fixture_backed` guard :905) and never publishes (fixture is not the live/sunday publish step) - benign but absent from the s7 exit table. SUNDAY market-stress halt IS reachable (the kill-switch `elif` :1022 precedes the `mode != MODE_SUNDAY` guard :1042) and is correctly covered by the `mode in {LIVE,SUNDAY}` always-send. prefetch (:240) and verify modes are untouched. Recommend adding FIXTURE and an explicit SUNDAY row to the exit-code table at Stage-0 for completeness.

## RATIONALE

The packet correctly identifies a real defect (a valid market-stress halt concludes the executor FAILURE and does not publish, blocking GitHub-native first-success coordination) and chooses the right shape of fix: split EXECUTION success from DOMAIN status in memory, promote only the typed `MARKET_STRESS` halt, and keep VALIDATION halts / crashes fail-loud. The mechanism is reachable (PipelineResult carries the discriminator), domain truth is preserved (no status flip), and the notification and consumer analyses are materially correct, including the non-obvious ZERO hazard from the dedup key now persisting once the halt publishes. The two REQUIRED changes are not disagreements with the direction; they close the gap between what the packet ASSERTS (s2's `errors==[]` discriminator, "no persisted field," "no masquerade") and what the FROZEN artifacts actually encode (a predicate missing the errors guard; an unspecified return carrier with a persist-and-exception-path trap). For a MATERIAL, HIGH-RISK packet whose product IS an exit-code/publish decision, the frozen design must state the invariants its safety depends on rather than inherit them silently from current code structure. Both fit inside one bounded correction cycle; no new material boundary is introduced by fixing them.
