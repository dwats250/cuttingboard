## REQUIRED CHANGES

### R-1. artifact_flow_map consumer wording reintroduces the Event-1-F1-forbidden `Consumers: (none)`

- Where: PRD-306 CHANGE SURFACE, lines 129-131:
  "the artifact_flow_map writer row records it with
  \"Consumers: (none) -- observe-only; manual inspection\"."
- Defect: the review-clean packet's Event-1 F1 correction (a GOV-2 section-1
  consumer-enumeration MATERIAL leg) mandates the artifact_flow_map row read
  `Consumers: Dustin -- human, manual local inspection (observe-only); machine
  consumers: none` and EXPLICITLY forbids `Consumers: (none)`
  (packet lines 500-503 and F1 correction lines 744-755:
  "observation consumer truthfully -- never `Consumers: (none)` (Event-1 F1)").
  `docs/sidecar_doctrine.md` treats the human reader as a valid
  observation-sidecar consumer; the packet chose deliberately NOT to reuse the
  generic `Consumers: (none)` pattern (which still exists elsewhere in
  `docs/artifact_flow_map.md`, e.g. `logs/watchlist_snapshot.json`). PRD-306
  reverts to the forbidden string. An implementer building the closeout
  artifact_flow_map M edit strictly from PRD-306 (as the charter directs) would
  write the exact string the CONFIRMED correction removed, re-opening the
  Event-1 F1 defect.
- Why it matters beyond fidelity: the human-consumer framing is what keeps
  GEX-1 consistent with VISION's "the system serves the trader / if a feature
  exists but does not change a decision, it should not exist." A row asserting
  `Consumers: (none)` claims the artifact serves no one, which is both false
  (Dustin reads it for discretionary context) and self-undercutting to the
  feature's VISION justification.
- Required correction (author, single GOV-1 cycle): replace the PRD's
  described writer-row consumer text so it names Dustin/manual local inspection
  as the human consumer and states machine consumers as none, matching the
  packet's mandated wording; do not carry the literal `Consumers: (none)`.

### R-2. R12 non-redistribution guard dropped the packet's exhaustive forbidden-key enumeration (Event-1 F7)

- Where: PRD-306 REQUIREMENTS R12, lines 415-417 (and BUILD-BINDING CONTRACTS,
  which carries no forbidden-key list). PRD R12 states only the general
  principle: "recursive scan of the artifact finds NONE of the forbidden
  raw-chain keys / row containers. FAIL: any per-contract raw-chain key or
  row-list container present in output."
- Defect: Event-1 finding 7 flagged R12 as a proxy ("R12 should freeze an
  exhaustive forbidden raw-row key/container guard rather than demonstrate only
  bid/ask"). The packet corrected it by FREEZING an exhaustive forbidden-key
  set in D8 / R12 (packet R12, line 539, enumerates the full set: `bid`, `ask`,
  `bid_size`, `ask_size`, `iv`, `theo`, `delta`, `gamma`, `theta`, `vega`,
  `rho`, `volume`, `last_trade_price`, `last_trade_time`, `open`, `high`,
  `low`, `close`, `prev_day_close`, `change`, `percent_change`, `tick`,
  `option`, `open_interest`, plus "no list-of-objects row container"). PRD-306
  omits that enumeration entirely. Under the charter's "PRD is build truth,
  packet is rationale only" designation, an implementer has no frozen forbidden
  set to test against and could satisfy PRD R12 with a non-exhaustive (bid/ask-
  only) scan -- exactly the proxy the correction removed.
- Required correction (author, single GOV-1 cycle): carry the packet's D8/R12
  exhaustive forbidden-key set into PRD-306 (in BUILD-BINDING CONTRACTS or in
  R12 itself), OR bind it by an explicit in-PRD reference to the frozen packet
  D8 enumeration, so the non-redistribution red test is exhaustive as Event-1
  F7 required, not illustrative. (An explicit binding reference is acceptable
  because the artifact is producer-constructed and the set is small and
  frozen; a bare general principle is not.)

## RECOMMENDED CHANGES

### r-1. LOC ceiling is honest but tight; keep the STOP-escalate live

The `<= 400` net-production-LOC ceiling matches the packet's bottom-up estimate
(packet section 8: Sigma ~= 380 + ~20 margin = 400, a ceiling honestly lowered
from the prior 420 after adding the validation surface), and Codex Event-2
CONFIRMED it. It is not dishonest: PRD-306 explicitly counts closed-vocabulary
declarations, load-time fail-loud validation, provenance/coverage carriers, and
PRD-198 red-test seams inside the 400, and names the ceiling breach as a hard
STOP requiring the GOV-2 amended-authority path. Given the density of the
frozen design (six-key first-failure exclusion accounting, three uniform
unavailable-object builders, five-class provenance block, coverage assembly,
zoneinfo ET conversion, atomic write, non-redistribution scan), the implementer
should treat the STOP-and-escalate as a live possibility, not a formality, and
not compress below readability to stay under 400. No PRD change required.

### r-2. Optional: note the packet-internal reason-key list-vs-order distinction

The PRD's per-row check order (line 228: missing-fields -> symbol parse -> root
-> expiry -> gamma -> open_interest) correctly reproduces the packet's
execution order (packet lines 428-429). The packet separately lists the six
reason KEYS in coverage-field order (missing_fields, invalid_gamma,
invalid_open_interest, unparseable_symbol, invalid_expiry, unexpected_root),
which is a different sequence from the execution order. This is inherent (the
coverage object names keys in schema order; rows are evaluated in check order)
and PRD-306 handles it correctly. No change required; noted only so the
implementer does not "fix" a non-bug by reordering the coverage keys to match
the check order.
