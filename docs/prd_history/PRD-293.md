PRD-293 — Idempotent dev bootstrap for remote/mobile sessions (script + thin SessionStart hook)

WHY NOW
Remote/mobile sessions (e.g. an Asher checkout) frequently start with the
`cuttingboard` package NOT installed into the active environment — `pip install
-e ".[dev]"` has not been run — so `import cuttingboard`, `pytest`, and `ruff`
fail on first use. The reconciliation plan names this F-5 ("remote-session env
unbootstrapped … a known trap"). QW-5 removes the trap with an idempotent
bootstrap that a thin SessionStart hook invokes, so a session starts ready
without an unconditional install-on-every-session anti-pattern.

GOAL
A standalone idempotent `scripts/dev_bootstrap.sh` that ensures the editable
dev environment exists (fast no-op when already ready, clear failure when it
cannot complete), plus a THIN `.claude/settings.json` SessionStart hook that
delegates to it — with every existing setting and permission preserved
byte-for-byte except the minimal SessionStart addition.

STAGE-0 PROOF (owner questions A-H — prove before build)
A. "Bootstrap already satisfied" == the active interpreter can `import
   cuttingboard` AND resolve the dev tools (`pytest`, `ruff`). Cheap probe:
   `python -c "import cuttingboard, pytest, ruff"` exits 0 → satisfied → no-op.
B. Failure removed: a fresh remote/mobile checkout with no editable install —
   `import cuttingboard` / `pytest` / `ruff` raise, so the agent's first tool
   call (pytest/ruff/import) errors. QW-5 makes the session self-heal.
C. Exact commands: (clean) probe fails → `python -m pip install -e ".[dev]"`
   into the active env, then re-probe; (already-ready) probe succeeds → print
   one line + exit 0, NO pip call; (partial, e.g. runtime deps present but dev
   extras missing) probe fails on `pytest`/`ruff` → same editable install
   (idempotent; pip is a no-op for already-satisfied requirements).
D. SessionStart safety: the probe is milliseconds; pip runs only on a failing
   probe, and `pip install -e` is additive (no destructive/global mutation).
   The hook adds no noticeable latency on a ready env.
E. Network/package unavailable: pip exits non-zero → the script prints a clear
   diagnostic and exits non-zero (fail-loud; never a silent success, never a
   retry loop).
F. Session-type coverage: SessionStart fires on session start (incl.
   resume/clear/compact). The fast idempotent probe makes repeated fires a
   cheap no-op, so firing broadly is desirable (that is exactly the
   remote/mobile case it exists for).
G. Human-runnable: `bash scripts/dev_bootstrap.sh` works standalone without
   Claude (the hook is only a convenience caller).
H. Permission invariants: the ONLY settings.json change is the SessionStart
   hook addition; the entire `permissions.allow` / `permissions.deny` arrays
   and the existing PreToolUse / UserPromptSubmit hooks are byte-unchanged.

REQUIREMENTS

R1 — Idempotent, non-destructive
Second invocation on a ready env is a fast no-op (no pip call); an already-ready
env is never reinstalled; no global/system state is mutated.
FAIL: the script runs `pip install` when the probe already passes, or mutates
state outside the project env.

R2 — Fail-loud
When bootstrap cannot complete (e.g. no network), the script exits non-zero with
a clear message; it never reports success on failure and never loops.
FAIL: a failed bootstrap exits 0 or retries destructively.

R3 — Thin delegating hook, zero permission drift
`.claude/settings.json` gains exactly one SessionStart hook that delegates to
`scripts/dev_bootstrap.sh`; no bootstrap logic is embedded in the hook; the JSON
stays valid; `permissions.allow`/`deny` and existing hooks are byte-unchanged.
FAIL: the hook embeds install logic, any permission entry changes, or the JSON
is invalid.

DATA FLOW
n/a (developer-environment tooling; no runtime/product data path).

FAIL CONDITIONS
- Unconditional install runs on an already-ready env.
- Any permission-array or existing-hook change.
- A failed bootstrap exits 0 (silent), loops, or mutates global state.
- The hook embeds logic instead of delegating.
- settings.json becomes invalid JSON.

VALIDATION (owner test expectations)
- Second invocation is a no-op / safe idempotent result (no reinstall).
- Existing-ready environment is not reinstalled.
- Missing prerequisites fail clearly (non-zero + message).
- Hook delegates rather than duplicates logic.
- settings.json remains valid JSON; permission surface unchanged (assert the
  allow/deny arrays equal main's).
- No unrelated file mutations.
