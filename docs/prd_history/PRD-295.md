GOAL
Make morning executor failures explicitly observable via a current-attempt Telegram alert, without changing execution authority, gate semantics, or observation-state semantics.

SCOPE
- Expose TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID to .github/workflows/cuttingboard.yml (currently absent) so a failure step can notify.
- Add one `if: failure()` notification path that reports ONLY current workflow truth, built via the EXISTING format_failure_notification formatter + send_telegram (no new helper).
- Add one deterministic $GITHUB_ENV failure-stage carrier the workflow maintains.
- Add executable red tests for the actual handler path.
- Preserve all existing execution gates and observation-state semantics.

OUT OF SCOPE
- No pytest/ruff removal; no exact-SHA CI proof; no actions:/checks: read; no CI_PENDING handling; no runtime-readiness checker; no post-execution artifact-gate change; no check_readiness.py morning extension; no daily DRIFT full-suite job.
- No Cloudflare / workflow_dispatch / slot / idempotency / staleness / CF-E2 / CF-D1b.
- No latest_run.json schema change; no new attempt ledger/artifact; no hourly workflow change; no PRD-293 lock-race fix; no broad notification refactor.

REQUIREMENTS

R1 — cuttingboard.yml job env exposes TELEGRAM_BOT_TOKEN and TELEGRAM_CHAT_ID from repo secrets (mirroring hourly_alert.yml), available to the `if: failure()` step.
FAIL: the failure step cannot read the Telegram secrets from the job environment.

R2 — an `if: failure()` step sends a Telegram alert whose content is derived ONLY from current workflow context (run identity, resolved mode if the mode step ran, current date/time from workflow context, the $GITHUB_ENV stage carrier), never from logs/latest_run.json.
FAIL: the alert reads, reflects, or dates itself from any logs/latest_run.json field.

R3 — the workflow maintains one deterministic failure-stage carrier via $GITHUB_ENV (written at the start of each major step; the runner applies $GITHUB_ENV writes post-step for any exit code, so the value reaches the terminal `if: failure()` step, last-writer-wins = the executing stage; a plain append cannot swallow the step's non-zero exit - the same mechanism as the existing PUBLISH_READY). Reportable stages are the helper-available ones (lint / tests / engine_doctor / execute / verify / render / commit / push); pre-install stages (mode_resolution, install) are NOT reportable, and job cancellation / the hard timeout are outside Slice-1 coverage.
FAIL: the alert reports a stage not deterministically derivable from workflow context, OR lists a pre-install / non-helper-available stage as reportable.

R4 — the failure message is built by the EXISTING cuttingboard.notifications.format_failure_notification (failed stage/class carried in its `reason` input; mode via notify_mode; current date stamped by the formatter), sent via send_telegram - NO new helper and NO second notification implementation. Coverage (option A): failures AFTER "Install dev dependencies" completes successfully (Lint / Test / execute / verify / render / commit / push - the motivating lint/test/execute class); pre-install failures are outside Slice 1 (no stdlib fallback).
FAIL: a new or duplicate notification implementation is added, OR coverage is claimed for a pre-install failure, OR the wording implies all workflow failures are notified.

R5 — observation state is preserved: no failed/blocked pre-execution attempt or notification writes or mutates logs/latest_run.json; existing pytest, ruff, and runtime execution gates are behaviorally unchanged.
FAIL: the change writes/mutates logs/latest_run.json on a failed attempt, or alters any existing gate's pass/abort behavior.

R6 — additive only: no CI/runtime authority is added; hourly_alert.yml is unchanged; a successful run does NOT emit the failure alert.
FAIL: hourly_alert.yml changes, OR a successful run emits the failure alert, OR any new gate/permission authority appears.
