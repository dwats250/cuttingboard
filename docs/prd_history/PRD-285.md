WHY NOW
`execution_policy.py` implements three "brakes" that gate whether an
already-qualified `ALLOW_TRADE` decision remains allowed: a daily trade-count
limit (`POLICY_SESSION_TRADE_LIMIT`), a cooldown between trades
(`POLICY_COOLDOWN`), and a consecutive-loss lockout (`POLICY_LOSS_LOCKOUT`).
Every one of them is fed by *recommendations and hypothetical evaluations
treated as if they were executed trades* — which they are not:

- `load_execution_session_state` (`execution_policy.py:76–119`) scans
  `audit.jsonl` and, for every prior same-session audit record, counts each
  `trade_decisions[]` entry whose `decision_status == ALLOW_TRADE` as a trade
  (`prior_trade_count += allow_count`, `:99–106`). An `ALLOW_TRADE` decision is
  a recommendation to the trader, not a fill.
- Those same recommendation rows establish `last_trade_at_utc`
  (`:107–108`), which then drives the cooldown predicate.
- `_load_consecutive_losses` (`:319–348`) scans `evaluation.jsonl` — the
  forward hypothetical-evaluation log — and counts `STOP_HIT` / negative-`R`
  rows as losses feeding `consecutive_losses`, which drives the live loss
  lockout. These are hypothetical outcome estimates of recommendations, not
  realized P&L on executed positions.
- Within a single run, `apply_execution_policy_to_decisions`
  (`:122–159`) increments an in-memory `trade_count` and sets `last_trade_at`
  after the *first* `ALLOW_TRADE` recommendation (`:155–157`), so a later
  otherwise-valid candidate in the same run is blocked by `session_trade_limit`
  or `cooldown` although nothing was executed. The existing test
  `test_first_valid_candidate_remains_allow_trade`
  (`tests/test_execution_policy.py:136–152`) asserts exactly this defect: the
  second valid candidate is `BLOCK_TRADE` with reason `cooldown`.

This violates VISION's `description-not-prediction` and
`the-system-serves-the-trader` principles: the system silently suppresses
genuine A+ recommendations on the basis of execution evidence it does not have.
Until a trustworthy execution/fill carrier exists, the honest behavior is
dormancy — no brake may fire on recommendation or hypothetical evidence.

GOAL
Make the trade-count, cooldown, and loss-lockout brakes fully dormant by
neutralizing their evidence sources — the only sources today being
recommendations and hypothetical evaluations — so that: (1) no historical
recommendation increments the trade count or establishes the last-trade time;
(2) no hypothetical forward-evaluation drives live loss lockout; (3) no same-run
`ALLOW_TRADE` recommendation increments the trade count or activates cooldown;
(4) the daily-limit, cooldown, and loss-lockout predicates and their reason
taxonomy remain in place but structurally cannot fire on the neutral state,
preserving a clean future seam where a trustworthy execution/fill carrier will
supply real evidence; while (5) leaving every other execution-policy gate
(qualification, low-confidence, chaotic-regime, stay-flat, macro-pressure, ORB,
size materialization) and the run's decision ordering exactly unchanged.

REQUIREMENTS

R1 — Historical recommendations do not increment trade count
`load_execution_session_state`, given an `audit.jsonl` containing prior
same-session records whose `trade_decisions[]` carry
`decision_status == ALLOW_TRADE`, returns `prior_trade_count == 0`.

FAIL: A loader call against an audit log with two prior same-session
`ALLOW_TRADE` recommendation rows returns `prior_trade_count != 0`.

R2 — Historical recommendations do not establish last-trade time
The same loader call returns `last_trade_at_utc is None` regardless of any
prior `ALLOW_TRADE` recommendation rows.

FAIL: The loader returns a non-`None` `last_trade_at_utc` derived from a prior
recommendation record.

R3 — Hypothetical evaluations do not drive live loss lockout
`load_execution_session_state`, given an `evaluation.jsonl` containing prior
same-session `STOP_HIT` / negative-`R` hypothetical rows, returns
`consecutive_losses == 0`.

FAIL: The loader returns `consecutive_losses != 0` from hypothetical
forward-evaluation rows.

R4 — Same-run recommendations do not increment trade count or activate cooldown
`apply_execution_policy_to_decisions`, given N otherwise-valid decisions and a
neutral `session_state`, returns every decision `ALLOW_TRADE`; no decision is
downgraded to `session_trade_limit` or `cooldown` on the basis of an earlier
same-run `ALLOW_TRADE` recommendation.

FAIL: In a two-otherwise-valid-candidate run the second decision is
`BLOCK_TRADE` with reason `session_trade_limit` or `cooldown`.

R5 — Brakes remain dormant end-to-end; other gates and taxonomy intact
With the loader neutral and no same-run mutation, the daily trade-limit,
cooldown, and consecutive-loss lockout never fire in production; the predicates
and the constants `POLICY_SESSION_TRADE_LIMIT`, `POLICY_LOSS_LOCKOUT`,
`POLICY_COOLDOWN` remain defined; and every other gate — `low_confidence`,
`chaotic_regime`, `stay_flat`, `macro_pressure_conflict`, `orb_inside_range`,
size materialization — blocks exactly as before.

FAIL: A genuine `low_confidence` / `chaotic_regime` / `stay_flat` /
`macro_pressure_conflict` / `orb_inside_range` / `size_rounds_to_zero` case
stops blocking; OR any of the three brake reason constants is removed; OR a
config threshold changes.

R6 — Deterministic ordering preserved
`apply_execution_policy_to_decisions` returns decisions in the same order as
its input for any input list.

FAIL: The output order differs from the input order.

R7 — No fabricated execution evidence; no schema growth
No fill is invented, inferred, or persisted; `ExecutionSessionState` from the
loader is always neutral; no new field, key, status, reason literal,
dependency, or artifact is added; the loader writes nothing.

FAIL: The change adds a schema field / contract key / status / reason literal /
dependency, or writes any fill/journal artifact, or the loader returns a
non-neutral `ExecutionSessionState` under current (recommendation/hypothetical)
inputs.

R8 — No consumer falsely claims a fill or a phantom brake block
For a clean multi-candidate run in which all other gates permit, every
recommendation is surfaced as actionable (e.g. `trade_visibility` ACTIVE), and
no consumer renders a `session_trade_limit` / `cooldown` / `loss_lockout` block
or otherwise represents a recommendation as an executed trade or fill.

FAIL: A clean two-`ALLOW_TRADE` run yields a `NEAR_MISS` / `BLOCKED` visibility
state carrying a brake reason for the second candidate, or any consumer
represents a recommendation as a fill.

  `audit.jsonl` / `evaluation.jsonl` no longer affects execution-policy state

  `TypeError` / `KeyError` / `ValueError` raises — which were about parsing the
  recommendation/hypothetical logs the slice stops treating as evidence. This
