## Focused hourly-test failure investigation

The two reported failures are a real test-isolation/order-dependence defect, but the evidence does not attribute them to PRD-304 behavior.

Both tests patch `cuttingboard.runtime.send_notification` to return `True` but do not patch or reset `get_last_notification_result`. The real sender normally updates the process-global `_last_notification_result`; the mock bypasses that update. `_execute_notify_run` then reads whatever result a prior test left in the global:

- `NOT_REQUESTED` plus `alert_sent=True` falls back to `SENT`, producing `notification_sent=True`.
- A stale `SKIPPED_NO_CONFIG` plus `alert_sent=True` is trusted as the richer result, producing `notification_sent=False`.

A direct no-write call to `_build_hourly_run_summary` reproduced both outcomes. Different suite ordering/global state therefore explains the focused failures and green full CI.

The two test bodies date to `93bc69f2` on 2026-04-30, and the rich-result preference/fallback dates to `97aa058f` on 2026-05-08. PRD-304 only adds the `operator_locked` summary input around this area; it did not introduce the global-result selection mechanism. This is pre-existing test debt, not harmless environment dependence and not a PRD-304 production regression.

The smallest deterministic test repair is to patch `get_last_notification_result` to a matching `SENT` result—or explicitly reset notification state—in:

- `test_hourly_run_writes_hourly_specific_artifacts`
- `test_hourly_run_failure_writes_hourly_failure_artifacts`
