WHY NOW
PRD-295 (merged @ #242) made silent post-install morning failures loud with an unconditional `if: failure()` Telegram. A valid follow-up remained (connector finding on 872869d, ruled VALID FOLLOW-UP by Dustin): on a live/sunday HALT/FAIL, runtime already SENDS and owns the notification (cuttingboard/runtime/__init__.py:897-903) but the summary is FAIL (:1413) so cli_main exits nonzero (:237), and the terminal step then sends a SECOND Telegram for the same attempt. Owner rulings (2026-08-11): NON-MATERIAL; CLASS INFRA; LANE HIGH-RISK; the ephemeral FAIL-owned runtime->workflow signal is an acceptable seam; materiality is not reopened unless the frozen boundary is falsified.

MAX EXPECTED DELTA

GOAL
Emit at most one Telegram for a FAIL/HALT outcome already owned by the runtime send, while leaving the generic PRD-295 workflow failure notifier the owner of every outcome it still owns.

SCOPE
- Runtime emits a unique ephemeral stdout sentinel `::CB_NOTIFY_OWNED_FAIL::` iff a notification was actually delivered (send succeeded) AND the attempt's summary status is FAIL. No persisted state; the notification decision (should_send/send_notification/save_last_state) is unchanged.
- The live/sunday execute step preserves the CLI exit code, detects that exact token, writes CB_NOTIFIED=true via $GITHUB_ENV, then preserves the original success/failure exit semantics (PUBLISH_READY still set only on success).
- The terminal `if: failure()` notifier suppresses itself iff CB_NOTIFIED==true; otherwise it behaves exactly as PRD-295.
- Executable proofs for every owned/not-owned path.

OUT OF SCOPE
- No persisted notification/attempt state; no logs/latest_run.json, contract, audit, report, payload, or persisted-schema change.
- No change to should_send / send_notification / classify_notification_priority / save_last_state, or to observation semantics.
- No hourly_alert.yml / alert_runner change; no Cloudflare/slot/idempotency coupling; no broad notification refactor.

REQUIREMENTS

R1 — runtime prints the exact token `::CB_NOTIFY_OWNED_FAIL::` to stdout (flushed) iff `artifacts.notification_sent` is True (a real send succeeded, runtime/__init__.py:918) AND the PRE-VERIFICATION summary status is SUMMARY_STATUS_FAIL (the :1413 value from `system_halted or errors`). Emitted only in execute_run's non-exception path, immediately after `_run_pipeline` returns (:266) and BEFORE the post-verification status override (:282-288) — reading the not-yet-overwritten `pipeline.summary["status"]` (or equivalently inside `_run_pipeline` after :1249); never in a `finally`. It MUST NOT key on the post-verification FINAL status: a :1413-SUCCESS attempt that only becomes FAIL via the verification override (:282-288) must leave the terminal free to fire. prefetch/verify/fixture never reach this point.
FAIL: the token is printed when notification_sent is False, or when the pre-verification status is SUCCESS, or is keyed on the post-verification final status, or is NOT printed when a :1413-FAIL attempt delivered a notification.

R2 — the token keys on ACTUAL delivery, never on mode or on "the run failed." A suppressed send (should_send False, alert_sent False) and a transport failure (send returned False) both leave notification_sent False and MUST NOT emit the token.
FAIL: the token is emitted for a suppressed send or a failed transport.

R3 — the live/sunday execute step captures the CLI exit code before `set -eo pipefail` can abort the step, detects the token, writes `CB_NOTIFIED=true` to $GITHUB_ENV, then exits with the original CLI code. Success/failure semantics and PUBLISH_READY gating are unchanged.
FAIL: the step's exit code differs from the CLI's, OR CB_NOTIFIED is set without the token, OR PUBLISH_READY gating changes.

R4 — the terminal notifier runs `if: failure() && env.CB_NOTIFIED != 'true'`; when CB_NOTIFIED==true the step is skipped (no generic send); otherwise it behaves exactly as PRD-295 (current-workflow-truth only, option-A import guard, stdlib fallback, no latest_run.json read).
FAIL: the terminal fires when CB_NOTIFIED==true, OR is skipped when CB_NOTIFIED!=true, OR any PRD-295 terminal behavior regresses.

R5 — only the live/sunday execute step can set CB_NOTIFIED. Because a FAIL send fails that step (so later steps skip) and a SUCCESS send never emits the token, a successful run's notification can never suppress a later-step (verify/commit/push) failure's terminal alert.
FAIL: prefetch/verify/lint/test/commit/push set CB_NOTIFIED, OR a successful-run notification suppresses a later-step failure alert.

R6 — the signal is ephemeral: a stdout token + a $GITHUB_ENV var, both per-attempt on a fresh runner. No persisted artifact/state/schema is added or changed, and the runtime notification-decision logic is untouched.
FAIL: any persisted-schema/state change, or any change to should_send/send_notification/save_last_state behavior.

R7 — hourly_alert.yml / cuttingboard.alert_runner and their notification behavior are unchanged; the change is confined to the pipeline workflow live/sunday execute step, its terminal step, and the runtime sentinel.
FAIL: hourly notification behavior changes.

runtime (notification_sent True AND PRE-verification summary status FAIL at :1413, read before the :282-288 override) -> stdout `::CB_NOTIFY_OWNED_FAIL::` -> live/sunday execute step (capture rc + grep token) -> `CB_NOTIFIED=true` in $GITHUB_ENV -> terminal `if: failure() && env.CB_NOTIFIED != 'true'` -> generic send skipped. logs/latest_run.json and the contract are never in this path.
