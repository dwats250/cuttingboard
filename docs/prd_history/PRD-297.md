REQUIREMENTS

R1 - The cuttingboard.yml `ruff` Lint step and `pytest tests/ -q` Test step are removed from the pipeline job; no ruff or pytest invocation remains in cuttingboard.yml. ci.yml still runs `ruff check cuttingboard/ tests/` and `pytest tests/ -q`.

R2 - The cuttingboard.yml `permissions:` block is exactly `contents: write` + `actions: read` - no `checks:`, no other scope, no removal of `contents: write`.
FAIL: the permissions block omits `contents: write`, omits `actions: read`, or contains any scope other than those two.

R3 - scripts/check_run_revision.py resolves the exact checked-out HEAD SHA and queries the Actions runs API filtered to event=push and workflow path `.github/workflows/ci.yml` with complete pagination, then assigns exactly one typed state and exits accordingly: CI_SUCCESS (the uniquely selected run is status=completed AND conclusion=success) -> exit 0; CI_PENDING (selected run not completed) -> bounded wait up to 120s re-polling, then exit non-zero if still not completed; CI_MISSING (zero matching runs) -> exit non-zero; CI_FAILED (selected run completed, conclusion!=success) -> exit non-zero; CI_PROOF_ERROR (any HTTP/auth/rate-limit/JSON-parse/schema/ambiguity failure) -> exit non-zero. Multiple matching runs select deterministically by highest run_number then most-recent created_at. No state degrades an unknown/error condition to exit 0.
FAIL: any non-CI_SUCCESS state exits 0; OR an HTTP/auth/parse failure is treated as success; OR a pull_request run (event!=push) or a non-ci.yml run can produce CI_SUCCESS; OR the selector is non-total (an input reaches no typed state).

R4 - scripts/check_runtime_readiness.py runs exactly these four deterministic, network-free checks and exits non-zero if any fails, zero if all pass: (a) `import cuttingboard.runtime` succeeds and `cli_main` is callable; (b) `pyarrow` imports and pandas resolves the pyarrow parquet engine; (c) `python -m cuttingboard --help` exits 0 and its output contains `--notify-mode`; (d) `logs/`, `reports/`, and `data/cache/` are creatable-and-writable. It performs no network call, no market-data read, no pytest, no ruff, and no repair/mutation of source or config.
FAIL: the readiness gate performs any network call, market-data/plausibility check, pytest, ruff, or repair; OR any of the four checks cannot fail when its prerequisite is broken.

R5 - The workflow records the CI-proven SHA and, immediately before the live/sunday pipeline invocation, re-reads `git rev-parse HEAD`; if it differs from the proven SHA the step fails named REVISION_DRIFT and the pipeline does not execute.
FAIL: execution proceeds when the current HEAD differs from the CI-proven SHA, OR no HEAD re-check precedes execution.

R6 - scripts/check_readiness.py gains an opt-in `--profile {hourly,morning}` (default hourly). The flagless invocation `python3 scripts/check_readiness.py` validates the exact current hourly artifact set with identical 0/1 exit semantics (bit-identical). `--profile morning` validates logs/latest_run.json run-health (status/outcome/errors/system_halted, reusing the existing run-health checks) and the freshly-rendered ui/dashboard.html + ui/index.html (required markers present, forbidden `pytest-of-`/`/tmp/` patterns absent). hourly_alert.yml is not edited.
FAIL: the flagless call changes hourly's validated artifact set, markers, forbidden patterns, or 0/1 exit behavior; OR hourly_alert.yml is modified.

R7 - The Commit artifacts step runs in the order execute -> generate/render/stage the CURRENT morning artifacts -> validate those staged current artifacts (`python3 scripts/check_readiness.py --profile morning`) -> commit -> push. The validation call sits after the render/copy of ui/dashboard.html + ui/index.html and before `git commit`; a non-zero validation exit aborts before any commit or push. The render still precedes the copy (render < copy preserved).
FAIL: validation runs before the current-run render, OR after commit/push, OR a failed validation still permits commit or push, OR the render/copy ordering is broken.

R8 - No pre-execution gate failure (CI_MISSING/PENDING/FAILED/PROOF_ERROR, REVISION_DRIFT, or a readiness failure) writes or mutates logs/latest_run.json; logs/latest_run.json keeps its schema and its single write path inside execute_run (the pre-execution gates precede execute_run).
