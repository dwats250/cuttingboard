WHY NOW
scripts/dev_bootstrap.sh acquires its interprocess lock with `mkdir "$LOCKDIR"` (:67) then publishes the pid in a SEPARATE step `printf '%s\n' "$$" >"$LOCKDIR/pid"` (:73), setting `_have_lock=1` only after (:77). Between :67 and :73 the lock directory exists with no pid file. `_dead_lock` treats a missing pid file as reclaimable (:49) and `_reclaim_lock` `mv`s the directory aside with no identity re-check (:58-59). A contender therefore reclaims a live owner's just-created lock, both processes proceed, the loser's `_lock_owned` fails, `_unlock` emits `FAIL [lock ownership lost]` (:28) and the process exits 2. This is the confirmed, deterministically-reproduced cause of the intermittent CI failure `tests/test_dev_bootstrap.py::test_concurrent_ready_starts_serialize_env_publication` (assertion :469), which failed on attempt 1 and passed on attempt 2 at the identical SHA in Actions runs 31601066278 (main b0c3cf3) and 31572245839 (PR #247, b8fea2c).

GOAL
Publish the owner pid ATOMICALLY with lock acquisition so a live owner's lock is never pid-less, closing the mkdir-to-pid publication race; preserve single-live-owner mutual exclusion, dead/malformed/orphan reclamation for the new file lock, owner-only release, atomic Claude env-block publication and unrelated user content, the ready/install paths, and the 60s bounded lock-wait; migrate any pre-upgrade lock DIRECTORY safely; and bound the acquisition-temp lifecycle so no permanently unowned artifact remains.

SCOPE
1. Representation: replace the `mkdir` directory lock with a `link()`-based lock FILE `LOCKFILE="$REPO_ROOT/.dev_bootstrap.lock"`.
2. Atomic acquisition (_lock): write the pid into a pid-tagged sibling temp `mktemp "$LOCKFILE.new.$$.XXXXXX"`, then `ln "$tmp" "$LOCKFILE"` in the contention loop (EEXIST is the mutex); on success `rm -f "$tmp"` and set `_have_lock=1`. The lock file, the instant it exists, already holds the pid.
3. Identity-safe reclaim of the FILE lock (_reclaim_lock): `ln "$LOCKFILE" "$grave"` to capture the current inode; judge liveness on the immutable captured inode; never reclaim a live/new owner; remove the original only if it is still `-ef` the captured dead inode.
4. Legacy-directory transition contract (see below).
5. Bounded, identity-safe acquisition-temp AND reclaim-grave lifecycle (cleanup on all paths + EXIT trap; a dead-owner sweep of both `.new.PID.*` acquisition temps and `.stale.PID` reclaim graves that never removes a live contender's).
6. `_lock_owned`/`_unlock` operate on the file; traps, `_env_update` (atomic `mv -f`), ready/install paths, and the 60s bounded wait are behaviorally unchanged (the wait bound is test-configurable via an env var defaulting to the production 60s).
7. Deterministic production-path tests for every interleaving and transition case; update the ceiling guard to 250.

LEGACY-DIRECTORY TRANSITION CONTRACT (owner-ratified 2026-08-12, ruling #3)
On upgrade a stale legacy DIRECTORY `.dev_bootstrap.lock/pid` may remain (e.g., after SIGKILL of an old-version process). The directory case is detected EXPLICITLY with `[ -d "$LOCKFILE" ]` BEFORE any `ln` attempt, never inferred from `ln` failing: `ln file dir` (no `-T`) links `file` INSIDE the directory and returns exit 0, so relying on `ln` to fail would drop a stray link into a possibly-live legacy lock and bypass this contract entirely. When `$LOCKFILE` is a directory:
- legacy directory with a live numeric PID: NEVER reclaim; wait normally (a real old owner still runs).
- legacy directory with a dead or malformed PID: reclaim safely (atomic rename aside, then remove).
- legacy directory WITHOUT a PID (pid file absent or empty): treat as ambiguous and NEVER automatically reclaim. Give it the existing bounded lock-wait opportunity to gain a PID (-> live/dead handling) or to disappear (old owner rmdir'd its own lock). If it remains pid-less through the bounded wait, FAIL LOUD with a specific legacy-lock diagnostic instructing the operator to confirm no dev_bootstrap process is active and remove the empty directory with `rmdir "$LOCKFILE"` (never `rm -rf`). A subsequent run proceeds after the empty directory is safely removed.
This intentionally accepts a rare, explicit one-time manual recovery after an old-version SIGKILL in the mkdir-to-pid window. It does NOT accept concurrent bootstrap execution, automatic reclamation of a potentially-live old owner, a generic or silent timeout, or a permanently spinning process. (The rejected move-and-restore policy was not identity-safe: after the directory is moved, a new-version process can publish the file lock before restoration, and an old owner that published its pid immediately before the move may already have returned from its old `_lock` and continue into readiness/install work while the new process owns the canonical path.)

REQUIREMENTS

R1 - Atomic publication. After `_lock` returns success, `$LOCKFILE` is a regular file whose sole line is the owner's pid; there is no reachable state in which `$LOCKFILE` exists as a live owner's lock without that pid (the pid is written to the temp before `ln`, and `ln` is the only creator of `$LOCKFILE`).
FAIL: a contender can observe `$LOCKFILE` present but pid-less for a live owner, OR acquisition uses `mkdir` + a separate pid write.

R2 - Identity-safe FILE reclaim. `_reclaim_lock` never removes a lock whose captured inode holds a live pid, and removes a dead/malformed/orphan lock only if `$LOCKFILE` is still `-ef` the captured inode; a new owner that acquires during the reclaimer's check is left untouched. Steady-state dead, malformed, and orphaned FILE locks are still reclaimed.
FAIL: a live owner's lock is reclaimed, OR a new owner's lock is removed by a reclaimer that judged a prior dead lock, OR a dead/malformed/orphan file lock is not reclaimed.

R3 - Legacy-directory transition (per the contract above). A live-pid legacy directory is never reclaimed; a dead/malformed-pid legacy directory is reclaimed; a pid-less legacy directory is never automatically moved or removed, is given the bounded wait, and — if it stays pid-less — causes a specific legacy-lock failure with an `rmdir` recovery instruction (never `rm -rf`). A pid appearing during the wait converts the result to live-owner contention.
FAIL: a pid-less legacy directory is automatically moved/removed, OR a live-pid legacy directory is reclaimed, OR the pid-less case ends in a generic/silent timeout or a permanent spin, OR the recovery instruction uses `rm -rf`, OR a new-version process acquires the canonical lock while a live legacy owner is recognized.

R4 - Acquisition-temp and reclaim-grave lifecycle. The acquisition temp is a pid-tagged same-directory sibling; `_lock` removes it on every success/timeout/failure return and the EXIT trap removes it on signal; a once-per-run sweep removes both `.new.PID.*` temps and `.stale.PID` reclaim graves owned by dead pids (file and empty-dir grave forms) and never a live contender's; after any later bootstrap no permanently unowned lock/temp/grave artifact remains.
FAIL: a live contender's temp/grave is swept, OR a dead process's temp/grave/lock survives a later bootstrap, OR a reclaim grave `.stale.PID` can persist after the owning process dies, OR the temp/grave name lacks the owning pid needed for identity-safe cleanup.

R5 - Preserved behavior. `_lock_owned`/`_unlock` remain ownership-guarded (only the owner releases); the EXIT/HUP/INT/TERM traps still release via `_on_exit`; `_env_update` remains a single atomic `mv -f` with owned-block-exactly-once dedup and unrelated-content preservation; the ready and install paths and install-failure stale-block removal are unchanged; the production lock-wait remains 60s (120 x 0.5s), test-configurable via an env var defaulting to those values.
FAIL: any of those behaviors changes, OR the production 60s bound changes, OR a non-owner can release the lock.

R6 - Portability. The script stays `#!/usr/bin/env bash`; it uses only `ln`, `mktemp <template>`, `[ -ef ]`, `kill -0`, `rm`, `rmdir`, `mv`, `printf`, `read`, `sleep`, and globbing — supported on the repo's Linux and macOS bash; no GNU-only flags (`mv -T`, `ln -T`). The acquisition temp is a same-filesystem sibling so hardlink publication is atomic.
FAIL: any GNU-only flag is used, OR the temp is created off the lock's filesystem, OR a non-bash-portable construct is required, OR directory-vs-file detection relies on `ln`'s exit status (which does not fail against a directory target -- an explicit `[ -d ]` test is required).

R7 - LOC ceiling. `scripts/dev_bootstrap.sh` net-production (non-blank, non-comment) count stays <= 250; the CI guard `test_script_stays_within_frozen_production_ceiling` asserts <= 250 (raised from 235 to the ratified ceiling, not packed to evade). A projected or actual count above 250 is a Section-8 RED owner-stop.
FAIL: the count exceeds 250, OR the ceiling guard is removed/loosened beyond 250, OR readability is sacrificed to pack under the count.

INVARIANTS
I1 One live bootstrap owner at a time; the successful `ln` (EEXIST mutex) is the sole acquisition.
I2 No contender reclaims a lock held by a live owner: a live file-owner always has its pid published atomically; a live-pid legacy directory is never reclaimed; a pid-less legacy directory is never automatically reclaimed.
I3 Ownership is externally visible atomically for the file lock (pid present the instant the lock exists); the pid-less legacy directory is treated conservatively (bounded wait then fail-loud), never as reclaimable.
I4 Dead, malformed, and orphaned FILE locks remain recoverable within one contention iteration; dead/malformed legacy directories remain recoverable; only the pid-less legacy directory requires a one-time manual `rmdir`.
I5 Only the owning process releases the lock; failure cleanup and signal handling cannot delete another process's lock; the acquisition-temp sweep never removes a live contender's temp.
I6 Claude env publication stays a single atomic `mv -f`; the owned block appears exactly once; unrelated user content and marker collisions are preserved (`_env_update` untouched).
I7 No new persisted authoritative record, dependency, credential, audience, or policy; the only durable artifacts are the lock file and (transiently) the pid-tagged acquisition temp and reclaim grave, all self-cleaning across runs (the dead-owner sweep removes abandoned temps and graves, so none persists past a later bootstrap).

DATA FLOW
_lock: sweep dead-owner temps -> mktemp pid-tagged sibling -> write pid -> loop { ln tmp LOCKFILE ? acquired : _reclaim_or_wait; sleep } -> rm tmp -> _have_lock=1. Contention: each iteration checks `[ -d "$LOCKFILE" ]` FIRST -- legacy directory: live-pid=wait, dead/malformed=reclaim, pid-less=wait (never reclaim); else `ln tmp LOCKFILE` acquires, or on EEXIST against a regular file, identity-safe _reclaim_lock. `ln` is never attempted against a directory. Timeout: if the blocker is a pid-less legacy directory, fail with the specific legacy diagnostic (rmdir), else generic contention fail. Release: _unlock (ownership-guarded rm) + EXIT trap (temp + lock cleanup). _env_update and ready/install paths unchanged.

AMENDED MECHANISM (to be implemented only after amended Gate A):
- Exact-pathname acquisition: replace the `ln` builtin/utility acquisition with the POSIX `link` UTILITY (`link "$src" "$dst"`), which calls link(2) directly: it fails EEXIST against an existing destination whether file OR directory and never links INSIDE a directory. This closes #2 (a legacy directory appearing between `[ -d ]` and acquisition can no longer be linked into; acquisition simply fails and the loop re-routes to legacy handling next iteration) -- empirically verified: `link src dir` fails EEXIST and creates nothing inside the directory, whereas `ln src dir` links inside. `link` is a coreutils/BSD utility (POSIX standardizes the `link()` function; the `link` command is present on both target platforms, Linux and macOS/BSD) and is NOT a new external dependency (as available as `ln`).
- Race-free serialized reclaim (closes #1): reclaim of a dead FILE lock is serialized through a reclaim-lock `RECLAIM_LOCK="$LOCKFILE.reclaim"` acquired with the same atomic `link` primitive, so only one reclaimer at a time judges-and-removes the dead lock; a new owner cannot acquire while the dead lock is present, and no second reclaimer can concurrently unlink a fresh owner. A stale reclaim-lock (left by a SIGKILLed reclaimer) is NEVER auto-stolen -- a read-pid-then-unlink self-heal would itself be a compare-then-unlink TOCTOU on a fixed-name mutex, reintroducing #1 on the SIGKILL-of-reclaimer path (amended-PRD review finding). Instead a present RECLAIM_LOCK makes `link` fail, the outer bounded loop waits, and on timeout the run FAILS LOUD with a specific manual-recovery instruction (rm the stale reclaim lock after confirming no bootstrap is running) -- the identical bounded-wait-then-fail-loud pattern already ratified for the pid-less legacy directory. RECLAIM_LOCK release is ownership-guarded by a PID-IDENTITY proof (NOT the superseded `_have_reclaim_lock` held-flag; see FINAL RATIFIED DIRECTION item 3): the EXIT trap removes RECLAIM_LOCK only after reading it and confirming it holds THIS process's pid, guarded by a `[ -e "$RECLAIM_LOCK" ]` existence test so an absent reclaim lock emits no spurious stderr. The non-atomic `[ -ef ]` compare-then-unlink is removed; the legacy dead/malformed dir reclaim keeps its `mv` (rename is atomically exclusive) and needs no separate serialization.
- Caught-signal cleanup (closes #5): _on_exit removes an owned in-progress RECLAIM_LOCK on EXIT/HUP/INT/TERM (by the PID-identity proof in FINAL RATIFIED DIRECTION item 3, existence-guarded), in addition to the acquisition temp; `_reclaim_lock` creates no `.stale.PID` FILE grave (dead file locks are removed inside the serialized RECLAIM_LOCK critical section), so only the legacy dead/malformed dir reclaim produces a `.stale.PID`; a SIGKILL leftover RECLAIM_LOCK is recovered by the next run's bounded-wait-then-fail-loud manual `rm` (never auto-stolen).
