WHY NOW
Two connected operational-truth failures let a broken or unhealthy hourly run be
represented as operationally healthy:

1. The hourly runner converts every runtime failure into exit code 0.
   `cuttingboard/alert_runner.py::main` is documented, in its own docstring, to
   "Run the hourly alert path and convert all runtime failures to exit 0"
   (`alert_runner.py:43`). It calls `_execute_notify_run(...)` at
   `alert_runner.py:97–102` and **discards its return value**, then falls through
   to `return 0` at `:122`. The `except Exception` backstop (`:103–122`) — the
   runner-level catastrophic path — also ends at that same `return 0`. So a
   system failure produces exit 0, the scheduled GitHub Actions job's "Run hourly
   alert" step reports success, and every downstream `if: ${{ success() }}` step
   (`.github/workflows/hourly_alert.yml`) runs and publishes.

2. Readiness validates key PRESENCE, not healthy STATUS.
   `scripts/check_readiness.py` requires `logs/latest_hourly_run.json` to contain
   the keys `("status", "outcome")` (`check_readiness.py:14–17`,
   `JSON_REQUIRED_FIELDS`) but `_validate_json_artifact` only checks
   `if field not in data` (`:46–52`) — it never inspects the VALUES. A
   structurally present but unhealthy artifact (a system-failure summary carrying
   `status="FAIL"` and a populated `errors` list) satisfies readiness.

Net effect: a non-throwing unhealthy outcome, or a thrown failure the backstop
swallows, can leave the hourly job green and the publish gate satisfied, so a
broken run is published as if healthy. This violates VISION's
`description-not-prediction` (the system asserts a healthy run it did not have)
and `the-system-serves-the-trader` (an operational-health signal the trader
relies on is silently false). This is CB-06.

SCOPE DISTINCTION (settled — not re-litigated)
- The operator is NOT signal-less today. A THROWN failure already attempts a
  Telegram notification and writes diagnostic artifacts before the runner
  returns: `_execute_notify_run`'s handler sends `format_failure_notification`
  and writes `traceback.txt` + the failure summary/contract
  (`runtime/__init__.py:620–673`); the runner-level backstop sends
  `"HALT - SYSTEM ERROR"` with audit reason `runner_level_exception`
  (`alert_runner.py:115–119`). None of that is removed.
- The narrow defect: job/workflow health may remain green; non-throwing
  unhealthy outcomes may not produce a failing process; readiness may accept a
  structurally present but unhealthy artifact.
- An ordinary market-driven `NO_TRADE` is NOT a system failure and MUST NOT fail
  CI. A successful but non-actionable market result is healthy.

TARGET INVARIANT
A broken or unhealthy hourly run must never be represented as operationally
healthy. A successful but non-actionable market result (`NO_TRADE`), and a
correct safety HALT (market-stress kill switch), may still be healthy.

Distinction among the operational classes (two gates, complementary):
- SUCCESS/actionable (row 1) and SUCCESS/`NO_TRADE` (row 2) — healthy; the run
  completed and produced a valid market decision (`system_halted=False`).
- Suppressed slot (row 3) — healthy; the runner correctly did nothing.
- Market-stress safety HALT (row 4) — healthy; the kill switch is a DESIGNED,
  COHERENT market-condition response. The run completed and emitted a HALT
  decision; its artifact carries `status="FAIL"`, `outcome="HALT"`, `errors=[]`,
  `system_halted=True`, and `_execute_notify_run` returns `status="SUCCESS"`.
- Data-integrity VALIDATION halt (row 5) — UNHEALTHY. This is a SECOND,
  non-throwing `system_halted=True` state, distinct from the kill switch: the
  system could not validate its anchor data (feed outage / stale or garbage
  SPY quote), halted, and — because the kill-switch block is gated behind
  `if not validation_summary.system_halted:` (`runtime/__init__.py:402`) —
  `hourly_kill_switch` stays False, so the summary is built with
  `status="SUCCESS"`, `outcome="NO_TRADE"`, `errors=[]` (`runtime/__init__.py:556–557,555`)
  even though `system_halted=True` (`:2076`). By `status`/`outcome`/`errors`
  ALONE this is indistinguishable from a healthy `NO_TRADE`; the `system_halted`
  carrier is what separates them. `HaltCause` (`validation.py:37–44`, PRD-180)
  exists precisely to distinguish a data/validation halt from a market-stress
  halt. Treated as UNHEALTHY: a data-integrity anchor failure inside the routine
  market window is an operational problem the operator must see as a red job, not
  a green publish.
- System failure (rows 6–7) — UNHEALTHY; the run could not complete. The in-run
  form carries a populated `errors` list AND `_execute_notify_run` returns
  `status="FAIL"`; the runner-level form is caught by the backstop.

Therefore existing carriers ALREADY distinguish every class — no new health
schema is required (see SCHEMA DETERMINATION) — but the discrimination is split
across TWO gates by what each can observe:
- RUNNER gate (`_execute_notify_run` return-dict `status`): SUCCESS = the run
  completed (rows 1,2,4,5); FAIL = an in-run system failure (row 6); plus
  reaching the runner-level backstop (row 7). The runner does NOT see
  `system_halted` (it is written into the artifact, not the return dict), so a
  VALIDATION halt (row 5) returns SUCCESS and the runner exits 0 — by design; the
  runner catches EXECUTION failures, not artifact-health incoherence.
- READINESS gate (written artifact `status` + `errors` + `system_halted`): an
  artifact is UNHEALTHY iff `status="FAIL"` AND `errors` non-empty (row 6), OR
  `system_halted=True` AND `status="SUCCESS"` (row 5 — a halt the status does
  not reflect; the market-stress HALT of row 4 is EXCLUDED because it carries
  `status="FAIL"`). Healthy/publishable: `status="SUCCESS"` with
  `system_halted=False` (rows 1,2), or the market-stress safety HALT (row 4:
  `status="FAIL"`, `errors=[]`, `system_halted=True`).
Row 5's job still goes RED (at the readiness step) and does not publish; the
runner exit-code fix (rows 6,7) and the readiness value-check (rows 5,6) are
complementary, and together no UNHEALTHY class is published green.

GOAL
Make every UNHEALTHY hourly run fail loud instead of being published green — an
in-run system failure (exception) produces a non-zero process, and both a
system-failure artifact and a data-integrity VALIDATION-halt artifact are
rejected by the publish gate — while leaving success, ordinary `NO_TRADE`, the
market-stress safety HALT, and suppressed-slot runs exactly as healthy as they
are today. The correction spans two complementary gates (runner exit code for
execution failures; readiness value-check for artifact-health incoherence) and
reuses only carriers the artifact already emits (`status`, `outcome`, `errors`,
`system_halted`).

SCOPE
- Runner exit-code (`cuttingboard/alert_runner.py::main`): capture the
  `_execute_notify_run(...)` return value (currently discarded at `:97–102`) and
  return a non-zero code when it does not represent a healthy completion —
  concretely, exit `0` iff `result.get("status") == SUMMARY_STATUS_SUCCESS`, and
  non-zero (proposed `1`) otherwise. Import `SUMMARY_STATUS_SUCCESS` alongside
  the existing `from cuttingboard.runtime import MODE_LIVE, _execute_notify_run`
  (`:56`). Change the runner-level backstop's terminal `return 0` (`:122`) to a
  non-zero return AFTER the existing notification/diagnostic attempt
  (`:103–121`) runs unchanged. The suppressed-slot early returns (`:81`, `:95`)
  stay `return 0` — suppression is healthy.
- Health-aware readiness (`scripts/check_readiness.py`): extend
  `JSON_REQUIRED_FIELDS` for `logs/latest_hourly_run.json` from `("status",
  "outcome")` to `("status", "outcome", "errors", "system_halted")` — all four
  are ALREADY written by `_build_hourly_run_summary` (`runtime/__init__.py:2060–2091`),
  so this adds no artifact field, only gate coverage. After presence, validate
  the VALUES: (a) `status` must be one of the canonical `{SUCCESS, FAIL}`;
  (b) `outcome` must be one of `{TRADE, NO_TRADE, HALT}`; (c) `errors` must be a
  list; (d) `system_halted` must be a bool; and reject the artifact as UNHEALTHY
  when it carries either failure/halt signal that a healthy publishable run never
  carries — (i) `status == "FAIL"` AND `errors` is a non-empty list (an in-run
  system failure), OR (ii) `system_halted is True` AND `status == "SUCCESS"` (a
  halt the run status does not reflect — the data-integrity VALIDATION halt;
  the market-stress safety HALT is EXCLUDED because it carries `status == "FAIL"`).
  PASS: `status == "SUCCESS"` with `system_halted is False` (TRADE / NO_TRADE),
  and the market-stress safety HALT (`status == "FAIL"`, `errors == []`,
  `system_halted is True`). An unrecognized `status`/`outcome`, a non-list
  `errors`, or a non-bool `system_halted` fails loud (malformed artifact). The
  canonical value sets are imported from the PUBLIC package surface —
  `SUMMARY_STATUS_SUCCESS`/`SUMMARY_STATUS_FAIL` from `cuttingboard.runtime`
  (re-exported via its `__all__`, `runtime/_constants.py:41–42`) and
  `OUTCOME_TRADE`/`OUTCOME_NO_TRADE`/`OUTCOME_HALT` from `cuttingboard.output`
  (`output.py:232–234`) — so the gate reads its source of truth, not a divergent
  proxy (PRD-198 #3). The workflow installs the package (`pip install -e .`)
  before `python3 scripts/check_readiness.py`, so the import is available at
  gate time.
- Unchanged by design: `_execute_notify_run`, `_build_hourly_run_summary`,
  `_failure_summary`, and every artifact field/value they emit; the daily path
  (`execute_run`, `runtime/__init__.py:247–322`) and its `_failure_summary`
  (`:2439`); the hourly workflow YAML (`hourly_alert.yml`) — its existing
  `if: ${{ success() }}` / `if: failure()` gating already routes correctly once
  the exit code is truthful (see WORKFLOW CONSEQUENCE); notification and
  diagnostic behavior on thrown failures.

SCHEMA DETERMINATION
No new health schema. Current-main evidence proves the existing values already
distinguish healthy from unhealthy AND safety-HALT from system-failure:
- Runner: `_execute_notify_run` returns `status="SUCCESS"` for every healthy
  non-throwing path (success, `NO_TRADE`, safety HALT) and `status="FAIL"` only
  for a system failure (`runtime/__init__.py:618` vs `:673`). The fix READS this
  existing return-dict key; it adds no field.
- Readiness: the written artifact's existing `status`, `errors`, and
  `system_halted` fields discriminate every class — an in-run system failure is
  uniquely `status="FAIL"` with a non-empty `errors` list (`:661`); a
  data-integrity VALIDATION halt is uniquely `system_halted=True` with
  `status="SUCCESS"` (`:2076` with `:556`); a market-stress safety HALT is
  `status="FAIL"` with `errors==[]` and `system_halted=True` (`:555–556`); a
  healthy run is `status="SUCCESS"` with `system_halted=False`. All three fields
  are ALREADY emitted by `_build_hourly_run_summary` (`:2060–2091`); the gate
  only READS them and adds none. It imports the canonical `SUMMARY_STATUS_*` /
  `OUTCOME_*` values from their defining/re-exporting modules rather than
  hardcoding literals (PRD-198 #3).
No contract/audit/report/payload/persisted-schema surface is added, removed,
renamed, or changed — the fix consumes three fields the artifact already carries
(GOV-2 §1 bullet 4 does NOT match).

SELECTED FAIL-LOUD BEHAVIOR (PRD-198 invariants)
- #1 fail-loud, never silent-fallback: a system-failure run exits non-zero and
  the readiness gate rejects both a system-failure artifact AND a data-integrity
  VALIDATION-halt artifact (`system_halted=True`/`status="SUCCESS"`), instead of
  the current substitute-exit-0 / pass-on-presence.
- #2 assert the resolved, not the requested: the runner keys on the ACTUAL
  return status of the executed run, not on the mere fact that `main` was
  reached; readiness keys on the artifact's actual `status`/`errors` values, not
  on key presence.
- #3 authoritative source, not proxy: readiness imports the canonical
  `SUMMARY_STATUS_*` / `OUTCOME_*` constants from their defining modules.
- #6 pin identities: the predicate compares against the canonical constant
  values, not free-typed string literals that could drift.
The rejected less-fail-loud alternative — "exit non-zero iff `status == "FAIL"`"
(predicate A) — would silently pass an unexpected/unknown status value and would
leave the non-canonical `"FAILED"` idempotency stub untouched; it is rejected in
favor of "healthy iff `status == SUMMARY_STATUS_SUCCESS`, else fail-loud"
(predicate B).

WORKFLOW CONSEQUENCE (`.github/workflows/hourly_alert.yml`)
No YAML edit is required; the existing gating already routes correctly once the
exit code is truthful:
- TODAY: the runner always exits 0, so the "Run hourly alert" step succeeds even
  on a system failure; every `if: ${{ success() }}` step (`Detect fresh hourly
  artifacts`, `Aggregate`, `Render and stage`, `Check hourly readiness`, `Commit`,
  `Push`) runs, and readiness passes on mere key presence — an unhealthy
  dashboard is published and the job is green.
- AFTER: a system failure exits non-zero, so the "Run hourly alert" step FAILS,
  the job status becomes failure, all `if: ${{ success() }}` steps SKIP (no
  render, no readiness, no commit, no publish), and the `if: failure()`
  `Upload failure artifacts` step RUNS (captures `traceback.txt`,
  `logs/latest_hourly_run.json`, contract, payload). The operator sees a red
  scheduled job plus the already-sent Telegram failure alert and uploaded
  diagnostics.
- Market-stress safety HALT and `NO_TRADE` still exit 0 and PASS readiness, so
  the workflow still publishes the HALT / no-trade dashboard exactly as today.
- The readiness gate has TWO roles after this change. (a) Against the in-run
  system-failure artifact (`status="FAIL"` + non-empty `errors`), it is
  defense-in-depth: that artifact only ever coexists with a non-zero runner exit
  (both come from the same exception path), so the readiness step is SKIPPED
  whenever the runner is already red — realizable as a standalone gate only for a
  future routing that returned `SUCCESS` while writing a failure artifact, or a
  stale failure artifact that survived `freshcheck` (declared defensive, Author
  discipline #3). (b) Against the data-integrity VALIDATION halt
  (`system_halted=True`, `status="SUCCESS"`), readiness is the PRIMARY and only
  gate that catches it: the runner returns SUCCESS (exits 0) and `freshcheck`
  sees a fresh payload, so the job proceeds to the readiness step, which FAILS,
  turning the job RED, skipping `Commit`/`Push`, and running the `if: failure()`
  diagnostics upload. This is a currently-realizable path (any in-window SPY/anchor
  data outage), not defensive-only.

NOTIFICATION / DIAGNOSTIC PRESERVATION
- The in-run exception handler (`runtime/__init__.py:620–673`) still sends the
  failure notification and writes `traceback.txt` + the failure summary/contract
  BEFORE `_execute_notify_run` returns `status="FAIL"`; the runner then exits
  non-zero. Nothing in that handler is touched.
- The runner-level backstop (`alert_runner.py:103–121`) still logs, builds the
  ASCII-safe body, and sends `"HALT - SYSTEM ERROR"` with audit reason
  `runner_level_exception` (and still never raises if the send itself fails);
  ONLY its terminal `return 0` becomes non-zero.

MALFORMED / MISSING ARTIFACT BEHAVIOR
- Runner: a malformed/failed run is caught by the in-run handler or the
  runner-level backstop; both now yield a non-zero exit with the existing
  notification + diagnostics. `_execute_notify_run` returning a dict without a
  `status` key (not a current-code path) is treated as unhealthy (fail-loud) by
  predicate B (`result.get("status")` is `None`, `!= SUCCESS`).
- Readiness: `check_readiness` already fails on a missing artifact
  (`_load_json` → "missing required JSON artifact", `:32–33`), invalid JSON
  (`:37–38`), or a non-object top level (`:40–42`). This PRD adds: an
  unrecognized `status`/`outcome` value, or a non-list `errors`, fails as a
  malformed artifact; and a well-formed system-failure artifact fails as
  unhealthy. Stale-but-fresh-looking artifacts are additionally gated upstream
  by the workflow's `freshcheck` (payload mtime vs run start) before readiness
  runs.

REQUIREMENTS

R1 — A system-failure hourly run exits non-zero
When `_execute_notify_run` returns a status other than `SUMMARY_STATUS_SUCCESS`
(current code: `SUMMARY_STATUS_FAIL` on the exception path), `alert_runner.main`
returns a non-zero exit code.

FAIL: A run whose `_execute_notify_run` returns `{"status": "FAIL", ...}` yields
`alert_runner.main(...) == 0`.

R2 — A runner-level exception exits non-zero, after notifying
When the runner-level backstop (`except Exception`) is reached, `main` still
attempts the failure notification and diagnostics (unchanged), and then returns
a non-zero exit code.

FAIL: A run whose pipeline import/execute raises (backstop path) yields
`main(...) == 0`, OR the backstop stops sending the `runner_level_exception`
audit/notification, OR `main` raises instead of returning.

R3 — Healthy, no-trade, safety-HALT, and suppressed runs still exit 0
A run whose `_execute_notify_run` returns `{"status": "SUCCESS"}` — including an
actionable `TRADE`, an ordinary `NO_TRADE`, and a market-stress safety HALT —
exits 0; a suppressed-slot run (outside window / same slot) exits 0; a
completed-but-failed-SEND run exits 0.

FAIL: Any of these healthy/suppressed cases yields a non-zero exit (in
particular, an ordinary `NO_TRADE` or a safety HALT failing CI).

R4 — Readiness rejects an in-run system-failure hourly-run artifact
`check_readiness()` returns a failure for `logs/latest_hourly_run.json` when the
artifact carries `status == "FAIL"` AND a non-empty `errors` list.

FAIL: A `latest_hourly_run.json` with `status="FAIL"` and `errors=["..."]`
produces no readiness failure.

R5 — Readiness rejects a data-integrity VALIDATION-halt artifact
`check_readiness()` returns a failure for `logs/latest_hourly_run.json` when the
artifact carries `system_halted == True` AND `status == "SUCCESS"` (the
non-throwing anchor-data/validation halt, whose `status`/`outcome`/`errors` are
otherwise identical to a healthy `NO_TRADE`).

FAIL: A `latest_hourly_run.json` with `system_halted=true`, `status="SUCCESS"`,
`outcome="NO_TRADE"`, `errors=[]` produces no readiness failure.

R6 — Readiness passes a healthy or market-stress safety-HALT artifact
`check_readiness()` returns no failure when `status == "SUCCESS"` AND
`system_halted == False` (any valid non-HALT `outcome`), or for the market-stress
safety HALT (`status == "FAIL"`, `errors == []`, `system_halted == True`,
`outcome == "HALT"`).

FAIL: A `SUCCESS`/`NO_TRADE`/`system_halted=false` artifact, or a market-stress
safety-HALT artifact (`status="FAIL"`, `outcome="HALT"`, `errors=[]`,
`system_halted=true`), produces a readiness failure.

R7 — Readiness fails loud on a malformed artifact
`check_readiness()` returns a failure when `latest_hourly_run.json` has a `status`
outside `{SUCCESS, FAIL}`, an `outcome` outside `{TRADE, NO_TRADE, HALT}`, a
non-list `errors`, or a non-bool `system_halted` (in addition to the existing
missing-file / invalid-JSON / missing-key failures, which are retained; the
required-key set grows to include `errors` and `system_halted`).

FAIL: An artifact with `status="WAT"` (or `outcome="NOPE"`, or `errors={}`, or
`system_halted="yes"`) passes readiness.

R8 — Producers, daily path, workflow YAML, and artifact values unchanged
`_execute_notify_run`, `_build_hourly_run_summary`, `_failure_summary`, the
daily `execute_run`, every emitted `status`/`outcome`/`errors`/`kill_switch`/
`system_halted` value, and `.github/workflows/hourly_alert.yml` are unchanged;
the dashboard renderer's output for the same artifact is unchanged.

FAIL: Any producer/daily/renderer/workflow test changes result, OR a diff
touches a file outside the FILES ceiling.
