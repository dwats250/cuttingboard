FINDING P1 (post-install import failures stay reportable): RESOLVED

The Notify-on-failure inline handler now computes `stage` before the import and
branches on it inside the except block. Evidence (.github/workflows/cuttingboard.yml,
Notify-on-failure step):

    stage = os.environ.get("CB_STAGE") or ""       # computed BEFORE the import
    ...
    try:
        from cuttingboard.notifications import format_failure_notification
        from cuttingboard.output import send_telegram
    except Exception:
        if not stage:
            print("pre-install failure (no CB_STAGE carrier); no alert sent (PRD-295 option A)")
            raise SystemExit(0)
        import urllib.parse, urllib.request
        token = os.environ.get("TELEGRAM_BOT_TOKEN", "")
        chat_id = os.environ.get("TELEGRAM_CHAT_ID", "")
        text = (f"cuttingboard: morning pipeline FAILED at stage {stage} (mode {mode}); "
                f"notification stack unavailable, minimal fallback alert. {run_url}").strip()
        if token and chat_id:
            payload = urllib.parse.urlencode({"chat_id": chat_id, "text": text}).encode()
            req = urllib.request.Request(f"https://api.telegram.org/bot{token}/sendMessage", data=payload)
            try:
                urllib.request.urlopen(req, timeout=15)
                print(f"failure alert sent (stdlib fallback): stage={stage} mode={mode}")
            except Exception as send_exc:
                print(f"stdlib fallback failed to send: {type(send_exc).__name__}")
        else:
            print("stdlib fallback: Telegram credentials absent; no alert sent")
        raise SystemExit(0)
    title, body = format_failure_notification(mode, "", reason)
    send_telegram(title, body)

Point-by-point:
1. stage computed before the import; empty CB_STAGE takes the Option-A no-op
   (raise SystemExit(0), no send); non-empty CB_STAGE takes a minimal stdlib
   urllib POST to the Telegram sendMessage endpoint. CONFIRMED.
2. The fallback text is built only from mode, stage, run_url (current workflow
   context). It never reads logs/latest_run.json; the string "latest_run.json"
   does not appear in the step. No stale observation field can leak. CONFIRMED.
3. Option-A preserved: a genuine pre-install failure (CB_STAGE unset -> stage
   == "") prints the Option-A line and exits 0 before the urllib import; no
   POST fires. CONFIRMED.
4. Not a broad second notification: the except path is a small urllib
   urlencode + POST, not a reimplementation of format_failure_notification.
   The normal (importable) path still calls format_failure_notification(mode,
   "", reason) + send_telegram(title, body) unchanged. CONFIRMED.
5. No secret printed: the token appears only inside the request URL string
   passed to urllib.request.Request. Every print() emits only stage, mode, or
   an exception class name; the token is never printed or logged, and is not
   placed in the message text. CONFIRMED.

The four previously-missing carriers now exist and are correct:
  - upload_engine_doctor: marker precedes the always() Upload step.
  - prefetch_cache_check: inline write in "Check OHLCV cache warmed".
  - prefetch_cache_save: marker precedes the Save OHLCV cache uses: step.
  - commit_message: marker precedes the always() Generate commit message step.

CRITICAL success()-guard confirmation:
  - The marker preceding the always() Upload step is if: success().
  - The marker preceding the always() Generate commit message step is
    if: success() && (job_mode==live || job_mode==sunday), i.e. success()-gated.
    CONFIRMED for both always() targets.
  - The success()-implicit steps confirm too: "Check OHLCV cache warmed"
    (if: prefetch), the "Save OHLCV cache" marker (if: prefetch && warmed),
    "Run prefetch/live/sunday", and "Verify run" all carry a plain if:
    expression with no status function, so GitHub inserts success() implicitly.
    Each is skipped when a prior step failed, so its inline/marker write cannot
    clobber an earlier failing stage. CONFIRMED.

The two GitHub-Actions semantics this relies on both hold: (a) a $GITHUB_ENV
write takes effect for SUBSEQUENT steps, and every carrier writes CB_STAGE at
the TOP of its step's run block, so a mid-step failure still exposes that
step's stage to the terminal notifier; (b) a plain if: expression is
implicitly success()-gated. A marker made unconditional or always() would
overwrite an earlier failing stage before the downstream always() step runs,
reintroducing the bug in reverse; neither always()-target marker is
unconditional.
