WHY NOW
PRD-304 (Manual Manageability Lock, COMPLETE @ #254, main e97f1fb) merged with
three lock-projection gaps found by the post-merge connector review, each a place
where the approved lock behavior is not actually realized:
1. `_build_hourly_contract` (cuttingboard/runtime/__init__.py) takes no
   `operator_locked` parameter, so the persisted hourly contract's
   `system_state.permission` is never set to the locked carrier. Its downstream
   consumers — the hourly payload (`build_report_payload` reads
   `system_state.permission`), the hourly HTML (`deliver_html` off that payload),
   and the dashboard renderer (derives `operator_locked` from that permission) —
   therefore do NOT reflect the lock, even though the hourly SUMMARY and hourly
   NOTIFICATION already do. The daily contract bakes the carrier in
   (`_build_and_finalize_contract`); the hourly builder is the one path that
   never got the same injection.
2. `_build_operator_lock_message` (cuttingboard/output.py) builds the daily
   NOTIFICATION body from `_alert_context_line`, which emits
   `REGIME | POSTURE | CONFIDENCE` (e.g. "RISK ON | AGGRESSIVE LONG | 0.80").
   Under the lock this LEAKS directional posture and confidence — exactly the
   action-bearing vocabulary R6 requires be stripped — contradicting the
   function's own docstring ("no ... posture").
3. The same function returns the title `f"{OPERATOR_LOCK_TITLE} {hhmm}"`, a
   non-canonical title. The one canonical OBSERVE-ONLY projection
   (`format_operator_lock_projection`, cuttingboard/notifications/formatter.py)
   returns `OPERATOR_LOCK_TITLE` verbatim and carries the timestamp in the body.

REQUIREMENTS

R1 — Hourly persisted contract carries the operator-lock permission
`_build_hourly_contract` accepts `operator_locked: bool`. When it is True, the
returned contract's `system_state["permission"]` equals
`config.OPERATOR_LOCK_PERMISSION`, so `build_report_payload(contract)` yields
`summary.permission == config.OPERATOR_LOCK_PERMISSION`. The single hourly call
site passes `operator_locked and not validation_summary.system_halted`, preserving
system-halt precedence (a halted hourly run keeps its halt permission, never the
lock carrier). When `operator_locked` is False the permission is unchanged from
the pre-PRD-305 behavior.

FAIL: A locked hourly run's persisted contract (or the payload/HTML built from it)
does not carry `config.OPERATOR_LOCK_PERMISSION` in `system_state.permission`; or a
halted hourly run has its halt permission overwritten by the lock carrier; or an
unlocked hourly run's permission changes.

R2 — Daily lock notification strips directional vocabulary and uses the canonical title
`_build_operator_lock_message` returns the title `config.OPERATOR_LOCK_TITLE`
verbatim (no appended timestamp). Its body's first line is
`config.OPERATOR_LOCK_PERMISSION`, and the body contains ONLY permitted fields:
timestamp, regime NAME, and data-health. The body MUST NOT contain the setup
posture or the regime confidence value, nor the `REGIME | POSTURE | CONFIDENCE`
context line emitted by `_alert_context_line`.

FAIL: `build_notification_message` on a locked contract returns a title other than
`config.OPERATOR_LOCK_TITLE` verbatim; or its body contains the setup posture, the
confidence value, or the ` | `-delimited context line.

R3 — Both fixes ship mutation-verified red tests
Each surface has a test that FAILS against the pre-fix code and PASSES after the
fix, plus a non-vacuity anchor proving the fixture actually carries the
leakable/lockable state.

FAIL: Either guard passes against the pre-fix code (cannot fail), or no
non-vacuity anchor exists.
