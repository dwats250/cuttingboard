WHY NOW
Execution permission is derived from market/regime policy only
(`apply_execution_policy_to_decisions`, cuttingboard/execution_policy.py:123);
there is no operator-availability input. A valid setup can therefore surface as
actionable across contract, dashboard, report, and notification surfaces while
Dustin is at work or otherwise unable to monitor a position. Dustin's settled
product direction is that when he cannot continuously manage a trade,
Cuttingboard must remain useful for observation but must not present a new trade
as actionable. This is a discipline lock, not a new trading signal.

GOAL
Deliver a manual two-state operator-availability lock (`CB_OPERATOR_AVAILABILITY`
∈ {AVAILABLE, CANNOT_MONITOR}, fail-closed) that, while locked, forces every
otherwise-allowed decision to BLOCK_TRADE at the execution-policy stage and
strips permission-to-trade and candidate-action vocabulary from every
action-bearing surface (contract projection, daily/hourly/qualify-only
notifications, dashboard, premarket/postmarket reports, CLI delivery, Market
Control Card), while leaving all analytical market observation, qualification,
grades, geometry, and `tradable` truth unchanged.

SCOPE
- Introduce `CB_OPERATOR_AVAILABILITY` with exactly `AVAILABLE` and
  `CANNOT_MONITOR` (trimmed, case-insensitive input; canonical uppercase value),
  read via `os.getenv` in cuttingboard/config.py (mirroring the existing
  secret-read pattern at config.py:54–55). Missing, empty, or invalid input
  resolves `CANNOT_MONITOR` (fail-closed). Invalid input logs a
  variable-name-only warning and never the raw value.
- Resolve the availability value EXACTLY ONCE at each runtime entrypoint
  (cuttingboard/runtime/__init__.py — daily, hourly, and qualify-only paths) and
  pass the frozen value downstream; no consumer re-reads the environment. The
  three workflows (`.github/workflows/cuttingboard.yml`, `hourly_alert.yml`,
  `dashboard_preview.yml`) relay the repository variable into the runtime.
- While `CANNOT_MONITOR`: force BLOCK_TRADE at EXECUTION_POLICY with reason
  `operator_cannot_monitor`, zero size, `policy_allowed=False`; empty
  `top_trades`; daily outcome NO_TRADE; apply the count truth table below;
  emit the dedicated locked-notification projection; suppress dashboard/report
  permission and action vocabulary; classify the new `OPERATOR_LOCKED`
  notification state ahead of `TRADE_READY`; admit the new Market Control Card
  permission string.
- Preserve analytical `system_state.tradable` as an unchanged market-condition
  fact; interpose the locked-permission check before every consumer that today
  reads `tradable` as permission.

OUT OF SCOPE
- No broker/order execution, position monitoring, automatic exit, portfolio
  state, or any capability to manage a trade. This lock only suppresses
  actionability; it never acts.
- No new dependency, credential, service, database, secret, UI control, schema
  key, schema version, persisted-artifact shape, audit shape, or notification
  channel. `qualified_count`, `tradable`, and all analytical fields keep their
  current schema and meaning.
- No time/location/device/employment inference and no automatic state change:
  no schedule, expiry, auto-unlock, or inferred availability. State changes only
  by Dustin editing the repository variable.
- No change to analytical market observations, qualification, grades, geometry,
  sizing inputs, regime, or data-provider truth.
- No change to existing halt/kill-switch precedence or notification audit
  semantics beyond the single explicit `OPERATOR_LOCKED` dedup state.
- No new field path added to docs/SCHEMA_MAP.md / docs/CALL_SITE_MAP.md (no new
  schema field is introduced; `CB_OPERATOR_AVAILABILITY` is an environment input
  and the lock permission is a value, not a key).

REQUIREMENTS

R1 — Operator-availability input and fail-closed resolution
`CB_OPERATOR_AVAILABILITY` is read in cuttingboard/config.py via `os.getenv`
(pattern per config.py:54–55). Input is trimmed and upper-cased; the canonical
resolved value is exactly `AVAILABLE` or `CANNOT_MONITOR`. Missing, empty
(after trim), or any value other than those two resolves `CANNOT_MONITOR`.
Invalid (present-but-unrecognized) input logs a warning naming only the variable
`CB_OPERATOR_AVAILABILITY` and never the raw value. There is no schedule,
expiry, auto-unlock, or inferred availability.
FAIL: any of {unset, empty, whitespace-only, unrecognized} resolves to
`AVAILABLE`; OR the raw invalid value appears in any log/stderr/artifact; OR any
automatic transition changes the resolved state without a repository-variable
edit.

R2 — Exact-once resolution, frozen threading
The availability value is resolved EXACTLY ONCE at each runtime entrypoint
(cuttingboard/runtime/__init__.py daily, hourly, and qualify-only paths) and the
frozen value is threaded to every downstream consumer; no consumer re-reads the
environment. The three workflows relay the repository variable into the runtime
environment (`.github/workflows/cuttingboard.yml`, `hourly_alert.yml`,
`dashboard_preview.yml`).
FAIL: any consumer calls the environment read for `CB_OPERATOR_AVAILABILITY`
after the entrypoint resolution; OR a single run resolves the value more than
once; OR any of the three workflows fails to relay the variable so the runtime
sees it unset (which, under R1, would fail-closed but breaks the intended
`AVAILABLE` operation).

R3 — Locked execution-policy block
Under `CANNOT_MONITOR`, a decision that the existing policy would otherwise
ALLOW becomes BLOCK_TRADE at stage `EXECUTION_POLICY`
(`POLICY_STAGE`, execution_policy.py:20) with `block_reason`
`operator_cannot_monitor`, zero size, and `policy_allowed=False`
(`POLICY_ALLOWED`, execution_policy.py:22; field contract_types.py:102). A
decision already blocked upstream retains its original `block_reason`. The block
is applied inside the per-decision policy path (`apply_execution_policy`,
execution_policy.py:159) and honored by the existing contract materialization
without a contract.py edit. System-halt permission continues to win over the
operator lock.
FAIL: a would-be-ALLOW decision remains ALLOW under lock; OR the block uses a
stage other than `EXECUTION_POLICY`; OR the reason is not `operator_cannot_monitor`;
OR size is non-zero or `policy_allowed` is True under lock; OR an upstream block
reason is overwritten by `operator_cannot_monitor`; OR a system halt is
downgraded by the operator lock.
