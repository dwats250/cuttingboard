WHY NOW
Connector thread 3687825284 on PR #177 found that PRD-272 (`LANE: MICRO`,
`CLASS: GOVERNANCE`, `docs/PROJECT_STATE.md` in `FILES`) violates the Lane
Downgrade Prohibition, which mandates `HIGH-RISK` whenever a PRD's `FILES`
intersects the HIGH-RISK FILES entry for its CLASS. The finding is correct.
Verification showed it is not local to PRD-272 — every MICRO/GOVERNANCE PRD
in the tree intersects the same list:

| PRD | HIGH-RISK FILES named in its own FILES | payload or pointer |
|-----|----------------------------------------|--------------------|
| PRD-155 | `PROJECT_STATE.md`, `PRD_REGISTRY.md` | pointer |
| PRD-156 | `PROJECT_STATE.md`, `PRD_REGISTRY.md` | pointer (payload is the moomoo deletion) |
| PRD-171 | `PRD_TEMPLATE.md`, `PRD_MICRO_TEMPLATE.md`, `PROJECT_STATE.md`, `PRD_REGISTRY.md` | PAYLOAD |
| PRD-202 | `CLAUDE.md` | PAYLOAD |
| PRD-272 | `PROJECT_STATE.md`, `PRD_REGISTRY.md` | PAYLOAD |

Two distinct defects produce that result.

**Defect 1 — `docs/PRD_PROCESS.md` contradicts itself.** Line 57 declares
registry and index bookkeeping (`docs/PRD_REGISTRY.md`, `docs/prd_index.json`)
"implicit in every PRD lifecycle and ... not enumerated in PRD `FILES`
sections," and instructs cross-reviewers to treat those edits as authorized
rather than as scope violations. Line 432 simultaneously lists
`docs/PRD_REGISTRY.md` as a GOVERNANCE HIGH-RISK FILE, making it a Prohibition
trigger. A file cannot be both outside `FILES` by rule and a `FILES`
intersection trigger. Every PRD closes by editing the registry, so read
literally this half of the trigger fires on all of them.

**Defect 2 — the Prohibition does not distinguish payload from pointer.**
`docs/PROJECT_STATE.md` is genuinely high-risk when a PRD rewrites it: it is
queue authority, and a wrong claim misroutes a fresh session — the exact
failure PRD-272 existed to repair. It is not high-risk when a closeout moves
the active-PRD pointer by one line. Treating both identically retires the
MICRO lane for governance bookkeeping entirely, which contradicts PRD-229's
ceremony tiering.

Ruled by Dustin 2026-07-30: fix the rule, not the five PRDs. Record the

STATED LIMITATION — THE GUARD CHECKS A DECLARATION, NOT A DIFF
R3's PROJECT_STATE.md branch verifies that an author DECLARED the touch as a
pointer, not that the resulting diff actually is one. A PRD can annotate
`(pointer)` and then rewrite the file wholesale, and the guard will pass. This
is deliberate: payload-vs-pointer is a judgment about intent that no static
check can resolve, and PRD-198 invariant 2 warns against asserting the
requested rather than the resolved. What the guard buys is that the judgment
becomes EXPLICIT and reviewable in the PRD text instead of silent. The
fresh-context review reads the diff and is the check on a mis-declaration; the
guard cannot be that check and does not claim to be.

Amendment 1 corrected this passage's load-bearing assumption. As first written
it asserted the fresh-context review as the compensating control while MICRO —
the lane the carve-out exists to permit — owes only an OPTIONAL `same-context`
review, so for the exact case that matters no diff-reader was guaranteed
(connector 3688464627). R5 now makes the review an obligation of using the
annotation, at any lane. The limitation stands as written only BECAUSE R5
exists; without it the annotation would be an unchecked self-declaration that
lowers ceremony, which is worse than the over-broad rule this PRD replaces.

Second, the FILES scan is line-oriented over the WHOLE `FILES` block, including
any explanatory prose inside it. A parenthetical note that merely *mentions* a
governance file — as this PRD's own FILES block mentions `docs/PRD_PROCESS.md:57`
— counts as naming it. Prose elsewhere in the document does not (the guard reads
only between the `FILES` header and the next section header, and a test pins
that). The residual false positive is left unfixed deliberately: it errs toward
MORE ceremony, never less, and the fix is to move the note out of `FILES`. A
heuristic that tried to separate entries from prose inside the block would trade
a harmless over-trigger for an evadable under-trigger.
