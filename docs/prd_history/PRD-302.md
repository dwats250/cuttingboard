SECURITY MODEL (ratified R.5 smallest lawful claim; packet R.1-R.6)
Slice A processes only PUBLIC, FIXED, non-sensitive inputs on an ephemeral
GitHub-hosted runner and DOES NOT claim filesystem or runner-credential
confidentiality via `drop-sudo`. Codex `:read-only` grants whole-filesystem
read (`:root = read`, no write, command-network Restricted). Sparse checkout and
working directory are minimization/navigation ONLY, never confidentiality
(R9). Safety rests on: no adversarial ingress (owner-only dispatch + fixed
synthetic event + trusted prompt); `unprivileged-user` credential isolation
proven at the post-merge probe (R6/R7); VERIFIED `OPENAI_API_KEY` protection
(non-dumpable proxy + `env -u` + key-free config -- packet R.3); least privilege
(contents:read, no id-token); denied writes/command-network; no
repository-authoritative/issue/PR/comment publication (a public ~90-day job log
and a one-day artifact exist and are acknowledged); zero authoritative effect.

REQUIREMENTS

R1 — Dispatch-only trigger
`campaign_control.yml` declares `on: workflow_dispatch` and NO other event.
FAIL: any of `issue_comment`, `pull_request`, `pull_request_target`,
`repository_dispatch`, `workflow_run`, `push`, `schedule` appears.

R2 — Owner-only actor + reviewed-main binding
The secret-bearing job runs only when `github.actor == 'dwats250'` AND
`github.ref == 'refs/heads/main'`, and checks out `ref: main`.
FAIL: the job lacks either guard, or the checkout ref is not `main`.

R3 — Sole-writer acceptance + topology-change RED
Authorization rests on the sole-writer model (R2), not on `allow-users`, which
is additive defense-in-depth only. Any change to writer/app topology (a new
repository writer, or a GitHub App/bot with equivalent dispatch/write
authority), or implementation evidence that the sole-writer condition is false,
is a RED owner stop requiring protected-Environment reconsideration before use.
FAIL: the workflow treats `allow-users` as the primary authorization boundary,
or omits the R2 actor guard.

R4 — Least-privilege permissions
Top-level and both jobs are `contents: read`. No `issues`, `pull-requests`,
`checks`, `actions`, `contents: write`, or `id-token`.
FAIL: any write scope or `id-token` appears anywhere in the workflow.

R5 — Secret path; Codex Action is the literal final secret-bearing step
`OPENAI_API_KEY` appears exactly once, only as the `openai-api-key` input of the
`openai/codex-action` step, which is the LAST step of the codex job. It is never
a job/step `env:`, never in a `run:`, and never present in the validate job.
FAIL: the secret appears elsewhere, any step runs after the Codex Action in that
job, or the validate job references the secret.

R6 — unprivileged-user credential isolation
`safety-strategy: unprivileged-user` and `permission-profile: ":read-only"`;
the staged public inputs are readable by the distinct Codex uid. Credential
isolation MUST NOT rest on `drop-sudo` (which does not block same-uid reads) or
on sparse checkout.
FAIL: `safety-strategy` is not `unprivileged-user`, or any confidentiality
claim rests on `drop-sudo`/sparse-checkout.

R7 — Blocking hosted-runner credential-isolation probe (proven post-merge)
A blocking step fails closed (exit 2, no proposal) if the Codex uid can read any
runner-owned credential, including `<runner-root>/.credentials`. This is the
mandatory named proof executed at the first post-merge `main` dispatch; it fits
within the five files (inline workflow step or a tool subcommand -- no sixth
file).
FAIL: no blocking probe exists, or the probe passes while a runner-owned
credential is readable by the Codex uid.

R8 — No persisted checkout credential
Every checkout in the codex job sets `persist-credentials: false`.
FAIL: any codex-job checkout omits `persist-credentials: false`.

R9 — Minimal checkout is minimization, not confidentiality
Sparse checkout is limited to the prompt, schema, and tool, and is documented
as minimization/navigation only.
FAIL: the PRD, workflow comments, or artifacts call sparse checkout or
`working-directory` a confidentiality boundary.

R10 — Inert model-output transport

`actions/github-script`, is written to a file without source interpolation, and
is never spliced into a `run:` body, filename, artifact name, or workflow
command.
FAIL: model output is interpolated into shell/filename/artifact-name/workflow
command anywhere.
