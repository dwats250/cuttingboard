## Round 1

FINDING (verbatim from the connector's PR review comment,
`cuttingboard/delivery/dashboard_renderer.py:2351`):

1. **P2 — Filter forbidden tokens before rendering WHY**
   "When `first_error` or `stay_flat_reason` is a literal `None`/`NULL`
   string, or contains `confidence=` without the exact `" (regime="`
   prefix expected by the existing split, this new line renders the
   raw value (for example, `WHY: NULL` or `WHY: confidence=0.25`).
   That violates PRD-281 R4 (`docs/prd_history/PRD-281.md:132-136`);
   sanitize all forbidden sentinel and confidence-bearing forms before
   emitting `.sys-why`, rather than relying on the narrowly formatted
   split."

DISPOSITION (PRD-228 triage; one correction pass, per the repo's
GOV-1 "at most one correction cycle" rule):

- Finding 1 — ACTIONED. The finding is correct and squarely inside the
  review's authorized scope (R4's raw-internals guard): the inherited
  `_ctx_reason` sanitizer only stripped `confidence=` when it appeared
  together with a preceding `" (regime="` in the exact combined shape
  (`str(_ctx_reason).split(" (regime=")[0]`), so a bare `confidence=`
  value with no `regime=` wrapper passed through unstripped -- and the
  literal `None`/`NULL` sentinel case was never checked at all,
  something R4 explicitly requires and the original PRD-219 code
  predates. Fixed by replacing the single conditional split with two
  independent `re.sub` strips (`regime=...`, `confidence=...`, each
  matched and removed regardless of the other's presence) plus an
  exact-match sentinel check that treats a bare `"None"`/`"NULL"`
  reason as no reason (the WHY line is suppressed entirely, not
  rendered empty or raw). Verified with three new discriminating
  tests -- `test_prd281_why_line_strips_bare_confidence_without_regime_prefix`,
  `test_prd281_why_line_suppressed_for_literal_none_string`,
  `test_prd281_why_line_suppressed_for_literal_null_string` -- each
  mutation-confirmed red against the pre-correction code, green after.
  Full `test_dash_system_state.py` + `test_dashboard_renderer.py`
  (390 tests) passes; full suite unchanged otherwise (3110 passed, 1
  xfailed, 2 pre-existing sandbox-only failures unrelated to this
  diff).

No adjacent or out-of-scope findings were raised in round 1; nothing
was deferred. Correction lands in commit `7bdd519` on PR #199.

FINDING (verbatim from the connector's PR review comment,

1. **P2 — Recheck sentinels after stripping internal suffixes**
   "Fresh evidence in the corrected code: when a reason combines a
   sentinel with engine metadata, such as `None (regime=RISK_OFF,
   confidence=0.25)` or `NULL confidence=0.25`, the sentinel check
   runs before the regexes; stripping the suffix then leaves `None` or
   `NULL`, which is assigned to `_ctx_reason` and rendered as `WHY:
   None`/`WHY: NULL`. This still violates PRD-281 R4, so apply the
   sentinel check to the sanitized result as well."

DISPOSITION (PRD-228 triage):

- Finding 1 — ACTIONED. Correct: round 1's fix only checked the
  sentinel (`_reason_str in ("None", "NULL")`) against the *original*
  string, before the `regime=`/`confidence=` strips ran, so a combined
  string like `"None (regime=RISK_OFF, confidence=0.25)"` fell through
  to the `else` branch (not an exact sentinel match), had its
  parenthetical suffix stripped by the `regime=` regex, and collapsed
  to the bare sentinel `"None"` -- which was never rechecked and
  rendered raw as `WHY: None`. Fixed by reordering: the strip step now
  always runs (guarded only by the pre-strip sentinel check to skip
  redundant work on an already-bare sentinel), and the exact-match
  sentinel check reruns on the post-strip result before assigning
  `_ctx_reason`. Verified with two new discriminating tests --
  `test_prd281_why_line_suppressed_for_sentinel_with_regime_suffix`,
  `test_prd281_why_line_suppressed_for_sentinel_with_confidence_suffix`
  -- both mutation-confirmed red against the pre-correction (round 1)
  code, green after. Full `test_dash_system_state.py` +
  `test_dashboard_renderer.py` (392 tests) passes; full suite
  unchanged otherwise (3112 passed, 1 xfailed locally with 2
  pre-existing sandbox-only failures unrelated to this diff; CI truth

## Round 3

SHA REVIEWED: 3d725decdde1fe7dd3317a325c5b1afe4d8e615e (the round-2

FINDING (verbatim from the connector's PR review comment,
`cuttingboard/delivery/dashboard_renderer.py:2355`):

1. **P2 — Strip embedded sentinel tokens from WHY reasons**
   "Fresh evidence after the earlier sentinel fixes: this
   equality-only post-check suppresses only reasons that reduce to
   exactly `None` or `NULL`. If `first_error` or `stay_flat_reason` is
   something like `provider returned NULL` or `reason: None`, the
   value remains truthy and is rendered by `.sys-why`, still violating
   PRD-281 R4's prohibition on literal sentinel tokens. Filter or
   suppress reasons containing these tokens, rather than checking only
   whole-string equality."

DISPOSITION (PRD-228 triage):

- Finding 1 — DISMISSED, false positive against this PRD's realistic
  scope. R4's "no literal None/NULL token" targets the
  sentinel-leaked-into-the-whole-field failure mode (`str(None)`
  coercion, or a JSON `null` naively unmarshaled to the string
  `"NULL"`) -- both already handled by rounds 1-2's exact-match check.
  The two fields this line renders (`run.errors[]` items,
  `payload.sections.validation_halt_detail.reason`) are short internal
  labels assigned directly by the pipeline, not sentences composed by
  string concatenation; there is no realistic current input path in
  this codebase producing a compound string like `"provider returned
  NULL"`, and auditing/hardening pipeline string-formatting is outside
  this renderer-only PRD's scope (`CLAUDE.md`: no runtime/pipeline
  changes; the seam inspection that authorized this slice scoped it
  the same way). Widening to word/substring matching would also invert
  the risk: a legitimate future reason using the ordinary English word
  "none" (e.g. "None of today's setups met the trend filter") would be
  silently suppressed even though it is a genuine, informative reason,
  not a sentinel leak -- a worse failure mode than the one being
  guarded against, and itself not a realistic input path today (the
  renderer's own internally-generated literals -- "no qualified
  setups", "candidates gated", "N setup(s) gated", "operational halt"
  -- never contain the word). Deferred as a hypothetical, not actioned.
  No test added; no code change. Thread reply and resolution posted on
  PR #199.
