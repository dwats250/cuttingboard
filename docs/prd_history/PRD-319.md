GOAL
Deliver the owner-ruled weekday PT cadence — 06:00 daily board, 06:30,
06:45, 07:00, 08:00..13:00 hourly snapshots — with Cloudflare as the
punctual primary clock for every slot, GitHub crons as delayed PT-truthful
fallbacks, explicit slot identity on every routine path, and a cheaper
hourly job, without weakening any publication or notification guard.

REQUIREMENTS

R1 — Worker: pure scheduledTime->slot resolution, CF primary everywhere
`workers/cuttingboard-clock/src/index.js` exports a pure function
`resolveSlot(scheduledTimeMs)` that converts `event.scheduledTime` to PT
wall-clock via `Intl.DateTimeFormat` with `America/Los_Angeles` and
returns exactly one of: `{workflow: "cuttingboard.yml", inputs: {mode:
"live", slot: "OPEN", ...}}` for PT 06:00; `{workflow:
"hourly_alert.yml", inputs: {kind: "routine", slot: "HH:MM", ...}}` for PT
in {06:30, 06:45, 07:00, 08:00, 09:00, 10:00, 11:00, 12:00, 13:00};
`{workflow: "cuttingboard.yml", inputs: {mode: "prefetch", slot: "PRE",
...}}` for the PRE cache-warm in BOTH seasons — the 12:50Z instant maps
to PRE year-round (PT 05:50 PDT and PT 04:50 PST both resolve PRE; the
pure function may match the 12:50 UTC minute for this one non-cadence
slot, since PRE is a UTC-anchored warm-up, not a PT cadence slot); or
`null` (no dispatch). The `scheduled` handler consults ONLY
`resolveSlot(event.scheduledTime)` — never handler wall-clock, never
`event.cron` for slot identity. `wrangler.example.toml` crons become the
PRE cron plus the three cadence expressions `0 13-21 * * 1-5`,
`30 13,14 * * 1-5`, `45 13,14 * * 1-5`.
FAIL: a table-driven Node test over both PST and PDT instants (including
every off-season twin AND the 12:50Z PRE instant in both seasons) finds
any instant resolving to zero-or-two dispatches where one is intended,
any slot identity taken from handler time, any weekday PT instant in the
target cadence with no dispatch, or a weekday 12:50Z instant in either
season not resolving PRE.

R2 — Hourly routine dispatch with explicit slot identity
`.github/workflows/hourly_alert.yml` `workflow_dispatch` gains inputs
`kind` (choice `routine`|`forced`, default `forced`) and `slot` (string,
default empty). A `routine` dispatch with a slot runs
`python -m cuttingboard.alert_runner --routine-slot "<slot>"`; every other
dispatch runs `--force-slot` exactly as today. A new pure resolver
`explicit_pt_slot(now_utc, slot_label, max_lag_minutes=...)` in
`cuttingboard/notifications/hourly_slot.py` returns the canonical UTC slot
iff the label parses as HH:MM, is a member of `ALLOWED_PT_SLOTS`, is not in
the future, and lags `now` by at most the existing `max_lag_minutes`; else
`None`. `alert_runner` maps `None` to the existing
`outside_routine_window` audit + exit 0, and applies the existing
same-slot dedup and post-send persistence unchanged.
FAIL: a routine dispatch resolves a slot other than the one named; an
out-of-window or future or non-allowed named slot sends; a plain
`workflow_dispatch` (no inputs) behaves differently from today's forced
path; or the mutation test (resolver returning the inferred slot instead
of the named slot) passes the suite.

R3 — Slot set: retire (6,0), add (6,45)
`ALLOWED_PT_SLOTS` becomes ((6,30),(6,45),(7,0),(8,0),(9,0),(10,0),(11,0),
(12,0),(13,0)). `tests/test_hourly_slot.py::test_allowed_pt_slots_exact_set`
pins the new exact set.
FAIL: `(6,0)` still resolves via `routine_pt_slot`; a 06:45 punctual
arrival fails to resolve `(6,45)`; or the exact-set test still passes with
any additional or missing member.

R4 — GitHub heartbeats: delayed, PT-truthful, identity-safe
`hourly_alert.yml` schedule becomes exactly: `40 13 * * 1-5`,
`40 14 * * 1-5` (intended 06:30), `55 13 * * 1-5`, `55 14 * * 1-5`
(intended 06:45, ruling Q4 — deliberately 10 minutes AFTER CF's 06:45
rather than the same-instant `45 13/14` pair, honoring the packet's
no-same-instant-peers correction), `10 14-21 * * 1-5` (hourly
heartbeats). The
alert step maps `github.event.schedule` for the four 06:xx crons to an
explicit `--routine-slot 06:30|06:45`; the hourly crons use the existing
inference path, which is unambiguous for them: with `(6,0)` retired, every
`10 14-21` fire in either season resolves to exactly its in-season hourly
slot or to no slot (off-season 06:10 PST has no eligible slot; 14:10 PDT
exceeds max-lag for (13,0)). Off-season 06:xx twins no-op via
`explicit_pt_slot` (future slot, or lag > max).
FAIL: any retained cron from the old set {`0 13`, `5 13`, `30 13`, `0 14`,
`5 14`, `30 14`, `0 15-21`}; a table-driven test over all new crons x both
seasons — evaluated at NOMINAL start times (a delivery-delayed hourly
heartbeat inferring the then-current slot is the pre-existing accepted
inference semantic per ruling Q9, not a FAIL) — finds an off-season twin
that sends, an in-season fire that resolves the wrong slot identity, or a
late-start (start-time shifted +6 to +20 min) 06:30 heartbeat that sends
as anything other than 06:30 or a no-op.

R5 — Pipeline: dual-seasonal PT-gated OPEN fallback (winter 06:00 primacy)
`cuttingboard.yml` replaces the `5 13 * * 1-5` OPEN fallback with
`20 13 * * 1-5` and `20 14 * * 1-5`; ALL THREE `5 13 * * 1-5` equality
literals in `cuttingboard.yml` are updated to recognize BOTH new
expressions — the `run-name` slot stamping, the `cb-open-coordination`
concurrency expression, AND the OPEN first-success pre-check step's
schedule-match `if:` condition — plus the `5 13` prose comments
(docs-match-code); `scripts/resolve_run_mode.py`
maps both new expressions to `live` and drops `5 13`. A new
`scripts/check_open_fallback_window.py` (mirroring `resolve_run_mode.py`
style: stdlib, fail-closed, unit-tested) gates ONLY schedule-event OPEN
runs, and gates by SEASON, not wall-clock window — so late in-season cron
delivery (the observed 45-55 min GitHub latency) still executes, while an
off-season twin always no-ops regardless of delay: given the fired cron
expression (from `github.event.schedule`), it prints `IN_SEASON` iff the
current `America/Los_Angeles` UTC offset matches the cron's season
(`20 13` <-> -07:00/PDT, `20 14` <-> -08:00/PST), else `OFF_SEASON_NOOP`;
an unknown cron or unresolvable offset exits non-zero (fail-closed). The
workflow no-ops the run (success, no publish, no notification) on
`OFF_SEASON_NOOP` before the dev-install step, exactly like the
first-success SATISFIED no-op path. `workflow_dispatch` runs (CF OPEN) and
Sunday/prefetch are never gated. `scripts/check_open_slot_satisfied.py`
and its satisfaction predicates are byte-untouched; the workflow's
event-selection literals around it are exactly the edits named above.
FAIL: an off-season twin (05:20 PST via `20 13`, or 07:20 PDT via
`20 14`) executes the pipeline; an in-season fallback delivered late (any
delay) is gated off; a CF `workflow_dispatch` OPEN is gated; on the
implemented head a `20 13`/`20 14` schedule-event run in season skips the
OPEN first-success pre-check step, or the implemented workflow still
contains the string `5 13 * * 1-5` anywhere; `resolve_run_mode` resolves
either new cron to anything but `live` (or resolves `5 13` at all); or
the gate script lacks a red test proving it exits non-zero on an unknown
cron or unresolvable offset.

R7 — At-least-once residual pinned (ruling Q10)

DATA FLOW
1. Cloudflare cron fires -> `resolveSlot(event.scheduledTime)` -> exactly
   one workflow_dispatch (pipeline OPEN/live at 06:00 PT; hourly
   routine+slot at cadence slots) or no-op.
2. Hourly routine dispatch -> `--routine-slot` -> `explicit_pt_slot`
   window check -> existing dedup -> existing `_execute_notify_run` ->
   existing publish tail. Forced path unchanged.
3. GitHub heartbeat cron -> (06:xx crons) `github.event.schedule` -> fixed
   intended slot -> same routine path; (hourly crons) existing inference.
4. Pipeline schedule fallback -> PT window gate -> first-success proof ->
   existing pipeline. CF dispatch path untouched except arrival time.
