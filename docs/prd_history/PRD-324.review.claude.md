## PRD-324 (A1-C) Independent Fresh-Context Design Review

VERDICT: APPROVE WITH REQUIRED CHANGES
REVIEWED SHA: e5849e80ef5ee7e55c9e2684e5a354fffb59143f (confirmed == frozen head; tree clean)

The core architectural move is sound and, importantly, the highest-risk element -- rewiring the global chart-slot award from the inline latch to the shared leaf -- is correctly analyzed and correctly gated by the pre-A1-C golden. I independently confirmed the leaf's predicate and ordering are byte-equivalent to the inline latch, so the winner does not change. But there are two design-completeness defects that must be fixed before Gate A (a certain-but-misfiled FILES omission, and an unpinned 1m timestamp convention that leaves R3/R4 unfalsifiable), plus several accuracy fixes.

Distinction used below: DESIGN defect = the spec is wrong/ambiguous/incomplete as written; IMPLEMENTATION concern = correct spec, verify at build.

### BLOCKING (must fix before Gate A)

B1. FILES omission -- `tests/test_dash_candidates.py` is a CERTAIN edit, mis-filed as conditional "confirm."
R7 (PRD-324:267-274, CHANGE SURFACE:184-187) deletes the renderer's `_GRADE_ORDER`. But `tests/test_dash_candidates.py:6` does `from cuttingboard.delivery.dashboard_renderer import (_GRADE_ORDER, render_dashboard_html)` and asserts its values at `tests/test_dash_candidates.py:363-372`. Deleting the renderer symbol breaks this import at collection time (repo-wide test failure), not just an assertion. The PRD parks this file in "FILES to CONFIRM ... include only if the rewire changes an assertion there" (PRD-324:159-160). A repo grep confirms `test_dash_candidates.py` is the ONLY out-of-cone importer of the renderer's tier-def copies. This is a known certainty, so it must move into the production FILES cone (or R7 must keep a renderer re-export, which then weakens R7's "absent from the renderer" clause). DESIGN defect (FILES completeness).

B2. The 1-minute timestamp labeling convention is never pinned, so R3/R4's completed-bin boundary is undefined against the actual producer output.
The producer stores each bar ts as raw `timestamp.isoformat()` from the yfinance index with no start/end normalization (`runtime/__init__.py:2716`), and `through = bars[-1][0]` is that same raw last-bar ts (`runtime/__init__.py:2741`). R4 (PRD-324:233-236) renders a 5m bin "only if its right edge is <= the symbol's `through`" and claims that equals "fully covered by observed 1m truth." That equivalence holds ONLY if the 1m bars are END/right-labeled. yfinance 1m bars are conventionally START-labeled (index = opening minute); under that convention a fully-complete bin `[09:30,09:35)` has its last constituent 1m bar at ts=09:34, so `through` reaches 09:34, not the 09:35 right edge -- and R4 would DROP the most recent complete 5m candle until the next minute's bar arrives. That is safe (never a partial bin) but silently contradicts the stated GOAL of a "full current-session" render (PRD-324:95-98). The design must (a) pin the producer/yfinance 1m ts convention (start vs end) as an explicit assumption, and (b) restate the completeness test in terms of it so the R4 mutation-red test can be authored unambiguously. As written, R4's parenthetical ("i.e., fully covered") is an unverified assertion. DESIGN defect (target C).

### REQUIRED (fix, not blocking review completion)

R-a. R3 vs R4 label-convention contradiction. R3 calls the bins "right-labeled" (PRD-324:225) while R4 emits each bin's label as "the bin-start" (PRD-324:236) -- that is left-labeled. Pick one convention and make R3 and R4 consistent; the FAIL/mutation lines depend on it. (Note: the `_day_label` short-string passthrough claim IS correct -- `_day_label("09:30")` returns "09:30" unchanged, setup_chart.py:73-83.)

R-b. R2 "verbatim" overclaim (TRUTH-adjacent). R2 states its bounds are "the packet Section 6 / Helm ruling 4 policy verbatim, not a new invention" (PRD-324:213-214). Packet Section 6 (packet:186-188) specifies `generated_at age <= 90 min` with NO future bound on generated_at; the 5m future skew applies only to `through`. R2 ADDS "generated_at ... is not in the future" (PRD-324:207-208). That is a sensible fail-safe strengthening, but it is NOT verbatim. Since freshness policy derives from a Helm ruling, either drop the added bound to match Section 6, or relabel it an intentional strengthening and carry it as a Helm-confirm item. DESIGN defect (target D).

R-c. R7 "exactly ONE place" is imprecise. A separate, pre-existing, identical-valued `GRADE_ORDER` lives at `cuttingboard/market_map_lifecycle.py:16` (public, own lineage, tested at `tests/test_market_map_lifecycle.py:26`). R7's "exists in exactly ONE place" (PRD-324:268) and its mutation test ("absent from the renderer") must be scoped to the renderer/leaf tier-def lineage and must define imported-vs-defined (if the renderer imports the leaf name and rebinds it module-level for B1 back-compat, "absent" needs a precise meaning). Otherwise a naive repo-wide assertion false-positives on `market_map_lifecycle`. (target F)

### RECOMMENDED

- R5 oracle clarity (target J). Once the inline latch is deleted, R5's "leaf over runtime inputs == pre-rewire inline winner" (PRD-324:250-252) can no longer compare against a live latch; the real non-circular guard is the pre-A1-C golden `tests/data/dashboard_pre_gex_golden.html` (rendered by the OLD latch) plus the frozen fixture `expected`. State this explicitly so the R5 test is not read as leaf-vs-leaf tautology. The golden is genuinely mutation-sensitive; confirm at build that the golden state actually exercises a chart-slot card.
- Input-source (not recompute) parity (target A). R5 should require feeding the leaf the SAME already-constructed `_price_bars` runtime object (`dashboard_renderer.py:3012`), not a reconstruction; the PRD cites the function def line `:1187` rather than the runtime value `:3012`. Also note the leaf must convert the renderer's UTC `now` (`dashboard_renderer.py:2347,3013`) to ET internally for the R2 session_date equality -- inputs are tz-aware so this is deterministic, but say so.
- Producer/renderer selection-input divergence (target B, handled but worth stating). The producer computes `primary_symbol` from `trend_history`/`_price_bars_rows` (`runtime/__init__.py:828-830`), while the A1-C renderer computes its primary from the price-bars sidecar `_price_bars` map. These are different bar sources with different age guards, so the two can legitimately disagree; R6 (PRD-324:258-265) correctly makes disagreement fall back to daily. This is safe, but it means intraday may be suppressed more often than "fresh snapshot exists" implies -- note it so it is not read later as a bug.
- Gap handling. `_intraday_symbol_bars` enforces strict-ascending/unique but NOT contiguity (`runtime/__init__.py:2690-2694`), so a 5m bin can contain an interior 1m gap; R3 would then aggregate <5 bars into a "complete" candle. State whether that is acceptable or must be gap-checked.
