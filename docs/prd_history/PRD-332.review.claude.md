## RECOMMENDED findings

### RC-1. The brief's chart-slot narrative overclaims for the "primary sits in a low tier" edge case it itself names in S3

`select_primary_card_symbol` (`cuttingboard/delivery/primary_selection.py:80-111`)
selects over `_CHARTABLE_GRADES` (A+/A/B/C — all four rendered tiers), not
over `_HIGH_GRADES` (A+/A/B, the workspace-eligible set). So the canonical
primary can legitimately be a C-grade symbol that never enters the
`>=2 high-grade` workspace at all. Brief section 3 acknowledges this exact
case only in the acceptance test ("S3 ... else first `sorted_syms` high-grade
symbol (fixture where the primary sits in a low tier)"), but its narrative
sentence a few lines earlier states unconditionally: "the default tab shows
the inline chart and every other tab keeps its `CHART >` disclosure." In the
low-tier-primary case that sentence is false — the workspace's default tab
(first workspace symbol, since primary isn't a workspace symbol) has
`chart_slot_available=False` and shows `CHART >` like every other tab; the
real inline chart renders where it always has, inside the low tier's
collapsed `<details>`. This doesn't break R1/S8 (chart-slot logic and
setup-chart count are genuinely untouched) and isn't a semantic or safety
issue, but the prose is internally inconsistent with the acceptance test two
lines below it, which could mislead an implementer who reads the narrative
and not the test list into thinking the default tab always has a chart.
Recommend a one-sentence correction in the brief/PRD before implementation to
avoid a spec-vs-test mismatch discovery mid-implementation.

### RC-2. `tests/data/setup_chart_legacy_oracle.json` is a byte-oracle dependency of a FILES-listed test but isn't itself in FILES

`tests/test_dashboard_renderer.py::test_prd330_golden_regions_and_embedded_svg_pinned`
(line ~4743) reads `tests/data/setup_chart_legacy_oracle.json` and hashes the
`system-state`, `tape-zone`, and `details-history` regions of both golden
files plus the A1-C golden's embedded candidate SVG. I verified none of the
three pinned `block_id`s is `watching-zone`, `candidate-board`, or
`alert-watchlist`, and that the SVG extraction is a document-level substring
split independent of what wraps the card — so on the evidence available, this
oracle JSON should NOT need editing when the two golden HTML files are
regenerated, and PRD-332's FILES section is not actually incomplete here.
Still, because it's a real byte-oracle in the direct dependency chain of a
listed file and is easy to overlook, recommend naming it explicitly in the
PRD/brief as "must stay green, not touched" for the implementer's tripwire
list, rather than leaving its safety implicit.

### RC-3. Workspace-symbol default-tab chart absence (RC-1's scenario) has no dedicated visual/acceptance check

Given RC-1, an operator whose primary happens to sit in a low tier will land
on a workspace default tab with a `CHART >` disclosure instead of an inline
chart — a real, if narrow, presentation state the V1/V2 visual acceptance
list doesn't call out as a fixture to capture. Not blocking (R4's fail-open
and identity/grade visibility guarantees are unaffected), but worth adding as
an explicit V-series case so implementation doesn't silently skip verifying
it looks acceptable.

## Dimension notes

**1. SEMANTIC LEAKAGE — PASS.** Traced `select_primary_card_symbol`
(`primary_selection.py:55-111`) and the renderer's `chart_slot_available=(sym
== _primary_card_symbol)` (`dashboard_renderer.py:3397`): both are read-only
inputs the design consumes, not values it computes or perturbs. The
workspace's default-`checked` rule and per-symbol CSS toggle only change
which already-rendered `_render_candidate_card` output is *visible*; the tier
walk, `_GRADE_ORDER`/`_TIER_DEFS`-based `sorted_syms` ordering, and the
`_HIGH_GRADES` set are all read, never mutated, by the design. No upstream
compute module is in FILES or implied by any acceptance test.

**2. OPERATOR-STATE VISIBILITY — PASS.** Verified the fail-open claim
structurally: the design's per-symbol hide rules all live in a dynamically
generated inline `<style>` block emitted at WATCHING-render time (not part of
the static `_CSS` constant used elsewhere for genuinely fixed selectors like
`#spy-levels`), and R4/S7 require every such rule begin `#setup-`. The static
`_CSS` constant has no existing `.setup-panel`/`.tier-group` hiding rule to
conflict with (grepped `:has(` in current `_CSS`: only one unrelated existing
use at the `#candidate-board:not(:has(.candidate-card))` line). The tab rail
(`.setup-tabs label`) is never targeted by any hide rule in the design, so
symbol+grade+lifecycle(+CHECK) for every qualified setup stays visible
regardless of selection.

**3. MANUAL_CHECK PRESERVATION — PASS.** Read
`tests/test_dash_manual_check_flag.py` in full. Its literal-count and
CSS-outside-phone-block assertions (`test_manual_check_flag_...`,
`test_manual_check_css_outside_protected_phone_block`) key on the exact
strings `"MANUAL CHECK"` / `class="candidate-state manual-check"`, not on
adjacency; only `test_manual_check_render_does_not_mutate_inputs` asserts the
adjacency direction (`ids.index("alert-watchlist") == ids.index("candidate-board")
+ 1`), and it — along with `tests/test_dash_candidates.py`'s equivalent
PRD-315 test — is correctly the one PRD-332 lists for inversion. The `"CHECK"`
tab token cannot collide with any `"MANUAL CHECK"` substring search (grepped:
no test anywhere asserts on a bare `"CHECK"` token). `_top_ids()`'s flat
`class="block` scan confirms nothing else acquires that class between the two
blocks post-move, so the adjacency invariant is a clean swap, not a new gap.

**4. SCOPE EXPANSION — mostly PASS, one clarification recommended (RC-2).**
FILES is otherwise complete: `docs/CALL_SITE_MAP.md` does not currently
record WATCHING order (grepped, no hits), so its "only if" condition
correctly resolves to no-op; `tests/dash_helpers.py`'s existing generic
`_market_map`/`_mm_symbol`/`_chartable` helpers are sufficient to build the
required >=2-high-grade and low-tier-primary fixtures locally inside the new
test file without a shared-helper edit. The "native radio + `:checked~`, no
JavaScript" claim is achievable: confirmed exactly one `<script` tag exists
today (`dashboard_renderer.py:2855`, the staleness banner), the technique
extends (not duplicates) the existing PRD-330 `#spy-levels` pattern, and the
dynamically-generated per-symbol inline `<style>` is a new but disclosed
extension of that precedent, not JavaScript.

**5. IMPLEMENTATION-READINESS — concern (R-1); otherwise PASS.** Independent
of the process finding above, the design content is concrete: FILES,
acceptance tests (S1-S11/B1-B6), and FAIL-lines all cite real, currently
existing symbols and line ranges (verified `_HIGH_GRADES`, `_TIER_DEFS`,
`_GRADE_CSS`, `_GRADE_ORDER`, `select_primary_card_symbol`,
`_render_candidate_card`'s signature, and the WATCHING emission block all
match the brief's description at the reviewed HEAD). The d2_seam tripwires

`test_r8_...` in `tests/test_dashboard_d2_seam.py` are all above-seam tests
that the design's own scoping (CSS-tail-append only, no above-seam markup
