CLASS

WHY NOW
ruff 0.16.0 broadened its default rule set, so CI went red on code nobody
touched. `pyproject.toml` declared `ruff>=0.4.0` (unpinned) with no ruff
configuration at all, so the lint contract was "whatever the installed ruff
defaults to" — a movable default that changed behavior with no diff. Same
class and file as PRD-264; PRD-198 invariant 6 (pin identities that matter:
dependency → declared AND locked).

MAX EXPECTED DELTA
Production LOC: 0. Config/test/doc only. `pyproject.toml` changes bounded to
one dependency string plus one `[tool.ruff.lint]` table; one new test file
(≤140 lines); no workflow edits; no new dependencies beyond replacing the
existing ruff declaration.

GOAL
Make the lint contract explicit and immovable: pin ruff to one exact version
and declare the historical default selection in-tree, so the `test` gate stops
depending on whichever ruff a runner happens to install.

SCOPE
- Pin the ruff dependency to an exact version: `ruff==0.15.22` (last 0.15.x,
  below the 0.16.0 default expansion; verified installable and green).
- Declare the historical default selection `["E4", "E7", "E9", "F"]` under a
  `[tool.ruff.lint]` table so the rule set is stated, not inherited.
- Add minimal discriminating tests that prove the pin, the selection, that
  ruff resolves the root config, and that `ruff check cuttingboard/ tests/`
  passes.
- Track this PRD in registry/index/state per existing convention.

OUT OF SCOPE
- Adopting the expanded 0.16 rule set (repo-wide convention change; own PRD).
- Any workflow-policy enforcement, version sweeps, nested-config firewalls,
  synthetic canaries, or a general ruff-governance system.
- Editing `.github/workflows/*` or anything under `cuttingboard/`.

REQUIREMENTS

R1 — Exactly one exact ruff pin
`[project.optional-dependencies]` declares ruff exactly once, as an exact
`==` pin (`ruff==0.15.22`), not a `>=` floor or a range.

FAIL: `tests/test_prd273_lint_baseline.py::test_exactly_one_exact_ruff_pin`
is red — the ruff spec is a range, is duplicated, or is absent.

R2 — Historical selection declared explicitly
`[tool.ruff.lint].select` equals `["E4", "E7", "E9", "F"]` exactly — the
pre-0.16 default, so nothing previously enforced is dropped.

FAIL: `test_lint_select_is_historical_set` is red — the selection differs or
the table is missing.

R3 — Ruff resolves the root config and the CI command passes
Ruff resolves the repo-root `pyproject.toml` (its `linter.project_root` is the
repo root) and `ruff check cuttingboard/ tests/` exits 0.

FAIL: `test_ruff_resolves_root_config` or `test_ruff_check_passes` is red.

DATA FLOW
pyproject.toml [tool.ruff.lint].select → ruff config resolution → `ruff check`
in ci.yml `test` job → green/red gate.

FAIL CONDITIONS
- ruff dependency is not exactly one `==` pin.
- `[tool.ruff.lint].select` != `["E4", "E7", "E9", "F"]`.
- ruff does not resolve the root pyproject as its config source.
- `ruff check cuttingboard/ tests/` exits non-zero.

WHAT THIS DELIBERATELY DOES NOT PROVE
Under the pinned ruff (0.15.22) the implicit defaults coincide with the
declared selection, so an unconfigured `--isolated` run is also clean. The
tests therefore do NOT assert that an unconfigured run fails — that coincidence
is exactly why the pin, not the defaults, is load-bearing: the protection holds
only while the version is fixed. The tests do not sweep ruff versions, firewall
nested configs, or model hostile configuration; those are out of scope.

STATED LIMITATION — RESOLVED-RULE COVERAGE DROPPED AT 8ca1969
After commit `8ca1969`, NO test asserts that ruff's RESOLVED rule set agrees
with the DECLARED `select` in `pyproject.toml`.

`8ca1969` rewrote `test_ruff_resolves_root_config` to parse ruff's reported
`Settings path:` and assert it resolves to the repository-root
`pyproject.toml`. That assertion is authoritative for CONFIG IDENTITY — it
proves which file ruff loaded, replacing a weaker `linter.project_root`
string-containment check. But it removed two assertions that the previous
version carried:

    assert "(E402)" in result.stdout          # E4 family present in resolved rules
    assert "line-too-long" not in result.stdout  # E5 absent from resolved rules

Those two were the only check that the rules ruff ACTUALLY RESOLVED matched
the selection this PRD declares. `test_lint_select_is_historical_set` does not
cover the gap: it reads `pyproject.toml` and asserts
`lint.select == EXPECTED_SELECT` — the DECLARATION only. Nothing now closes the
loop from declaration to resolution.

This is the same declared-vs-resolved distinction the PRD exists to defend
(PRD-198 invariant 2: assert the resolved, not the requested). The pin and the
explicit `select` are declarations; a test that only re-reads the declaration
cannot detect a ruff that loads them and then resolves something else.

Recorded as a stated limitation, not a defect: the merged behavior is correct
and the config-identity assertion is stronger than what it replaced. The gap is
in coverage, not in the lint gate itself. Restoring resolved-rule agreement is
queued as PRD-274 and is deliberately NOT folded into this PRD's closeout
(Dustin's ruling, 2026-07-26).
