## FINDINGS

### F1 — Postmarket counts a refused symbol as both qualified and rejected
**Label: schema ambiguity. Severity: MEDIUM.**
`cuttingboard/reports/postmarket.py:216-220` sets
`trade_summary.qualified_count` from `audit_summary["qualified_count"]`,
which is `qual.symbols_qualified` (`cuttingboard/contract.py:460`) and still
includes a refused symbol, while `rejected_count` (`postmarket.py:219`) now
also counts it. For a sole-candidate all-refused run the postmarket report
reads `qualified_count: 1, rejected_count: 1` over one symbol. The dashboard
survival funnel deliberately resolves this the other way — it subtracts the
refusal out of QUALIFIED (`dashboard_renderer.py:2487`) so the four counts
sum to SURFACED. The two consumer surfaces therefore disagree on whether a
refused symbol is qualified. R6's FAIL line is nonetheless satisfied (the
breakdown key exists and `rejected_count` is not zero), so this sits just
outside R6's letter and inside the GOAL's "without contradiction". Not
fixed here; a reconciliation would need its own bounded scope.

### F2 — The end-to-end test injects a stubbed refusal, not a real one
**Label: factual drift. Severity: LOW.**
`docs/prd_history/PRD-283.md:336-339` (VALIDATION) states the
`_run_pipeline` integration test will "generate a real refusal". The landed
test at `tests/test_runtime_decision.py:802-809` monkeypatches
`runtime.build_option_setups` with `_refusing_build`, a stub that appends a
hand-constructed `OptionRefusal` and returns `[]`. Every forwarding leg
(contract, audit, postmarket, premarket, HTML, notification, CLI) is
genuinely exercised and would redden if broken — but the producer predicate
and its arithmetic are never executed in the integration path, so PRD-198
invariant #2 ("assert the resolved, not the requested") is only partly
honored at this seam. Mitigated: the predicate itself is covered by eight
unit tests in `tests/test_phase5.py::TestSmallestContractRefusal` against
live constants, and mutation A/B/C above prove those are discriminating.

### F3 — `notification_state_key` is an unenumerated `rejections` consumer
**Label: factual drift. Severity: LOW.**
`cuttingboard/notifications/state.py:56-62` derives the notification
dedup/suppression key from `contract["rejections"][0]["reason"]`. It reads
the surface PRD-283 extends, yet appears neither in § CHANGE SURFACE's
consumer enumeration nor in § OUT OF SCOPE as retained-with-reason. The
behavior change is benign and arguably an improvement — because
`_options_sizing_rejections` appends *last* (`contract.py:422`), the key is
unchanged whenever any other rejection exists, and a sole-refusal run now
keys on `SMALLEST_CONTRACT_EXCEEDS_BUDGET` instead of falling back to an
empty `stay_flat_reason`, which distinguishes a refused run from a plain
no-setup run for MEDIUM/LOW suppression. No defect; the gap is in the
downstream-consumer audit, not in the code.

### F4 — The daily run summary drops the refusal with no representation
**Label: factual drift. Severity: LOW.**
`cuttingboard/runtime/__init__.py::_build_run_summary` (`:1339-1414`)
receives `option_setups` but not `option_refusals`, so `logs/latest_run.json`
carries no representation of a sizing refusal. PRD-283 § SCOPE says the
refusal is represented "at every consumer that today drops it", and this

results — `candidates_qualified` is computed from `ALLOW_TRADE` decisions
(`runtime/__init__.py:1363`, `:1400`), which is correctly 0 on an all-refused
run — so this is an omission, not a false statement.

## DRIFT CHECK (PRD-186)

**Does the change conflict with a `VISION.md` non-goal or operating
principle? No — it advances one.**

- *Description, not prediction.* The refusal is deterministic arithmetic on
  present-tense inputs (equity × per-trade pct × correlation modifier vs.
  strategy max loss × 100). No forecasting is introduced.
- *Read-only sidecars by default.* The change does mutate the decision
  contract (a new `rejections[]` stage value, an `options_refusals` audit
  field, an `options_sizing` postmarket key). The principle governs *new
  observational features*; this is a correction to the decision path itself,
  where sidecar treatment would be exactly wrong — a refusal that lived in a
  sidecar would leave the contract still claiming a trade. Both schema
  changes are additive and were declared in § MAX EXPECTED DELTA.
- *Cuts before additions.* The change removes the `max(1, …)` floor before
  adding the carrier; the additions exist to keep the removal honest at each
  consumer.
- *The system serves the trader.* This is the clearest alignment. VISION's
  third question is literally "whether a candidate clears the discipline
  gates **and sizes to a real position**, or whether the honest answer is no
  trade". The pre-change floor answered that question falsely; the change
  makes it answer truthfully, and it changes what the trader does.
- *The system must match its documentation.* This is where the drift is —
  see below.
- No new prediction logic, no new sidecar without a consumer, no new module.

**Does the change leave any `docs/PROJECT_STATE.md` claim stale? Yes, one —
by omission, and it is known.**

- `docs/PROJECT_STATE.md` has no PRD-283 entry at all: no bullet in the
  active/recent block (which carries CB-01 and CB-04..CB-07) and no row in
  the recently-completed table. A reader of PROJECT_STATE alone would
  conclude CB-02 never landed, while the code is on `main`. This is the
  docs-match-code divergence VISION names as "the failure mode that produced
  sprawl". Owned by the separate TRUTH-SYNC packet per the review charge;
  recorded, not fixed. (See F6 for the registry/index/PRD-header half.)
- **Not stale:** the test-baseline claim at `docs/PROJECT_STATE.md:217`
  ("3245 passing, 1 xfailed") reconciles with this worktree's full-suite run
  (3241 passed + 4 environment-only failures + 1 xfailed = 3245/1).
- No review artifact under `docs/prd_history/` was found to have skipped its
  DRIFT CHECK as a consequence of this change.
